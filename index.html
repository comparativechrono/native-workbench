A first session

Ten minutes to see what the workbench does. Each step has a ▶ button that does it for you – but try typing too.

1 · A notebook

The Notebook tab opens with welcome-python.ipynb. Click into the first grey cell and press Shift+Enter: the code runs, its output appears below, and the next cell is selected. Python starts in the background when the notebook opens; if it is not ready yet, the first run waits for it – a few seconds.

Run the cells one after the other. You will read a table with pandas, draw a histogram, read protein sequences with Biopython, call samtools from a cell, and fetch a protein from UniProt. Everything is saved as you go.

2 · The terminal

The Terminal tab is a Linux shell (bash) with real programs. The example data is in /data/examples:

ls -R /data/examples
head -4 /data/examples/reads/NA12878_R1.fastq
samtools faidx /data/examples/reads/reference.fa human_CYP2C19:11590-11640

Type help for the list of programs, and man samtools for examples of one of them.

3 · Your files

Your own files live in your home folder, ~ (/home/user). The notebooks, the terminal and the Files tab all see the same files: a file that a terminal command writes can be read by a notebook a moment later.

mkdir -p ~/first && cd ~/first
seqtk comp /data/examples/sequences/myoglobins.fasta | cut -f 1,2 > lengths.tsv
cat lengths.tsv

Notebooks

Jupyter-style notebooks in Python or R. Each notebook is an .ipynb file among your files – saved as you work, and ready to download and open in Jupyter, JupyterLab, VS Code or Google Colab.

Open, start and rename

  • Notebooks (top left) lists your notebooks and starts new ones: New Python notebook, New R notebook, Open a notebook from my computer… (an .ipynb file). The same menu makes a copy, shows the notebook in Files, or deletes it.
  • The name next to it is the file name: click it, type a new one and press Enter.
  • New notebooks go into ~/notebooks. Any .ipynb file opens here: click it in the Files tab, or type open NAME.ipynb in the terminal.
  • Drop .ipynb files from your computer onto the notebook to open them; other files you drop are added next to the notebook.

Cells

A notebook is a list of code cells and text cells. + Code and + Text add one below the selected cell.

Shift+Enter or ▶ Runrun the cell and go to the next one
Ctrl+Enterrun the cell and stay on it
Alt+Enterrun the cell and add a new one below
Run allrun every cell from the top, in order

The number in brackets, [3], shows the order in which the cells ran; […] means the cell is waiting for its turn, [*] that it is running. Output appears below the cell: printed text, tables, plots, and errors (with a hint on what they usually mean).

The ⋯ of a cell changes it into a text or code cell, moves it, duplicates it, clears its output or deletes it.

Text cells

Text cells use Markdown: # Heading, **bold**, *italic*, - a list, `code`, [a link](https://…) and tables. Shift+Enter shows a text cell formatted; double-click it to edit it again.

Keys for a selected cell

Press Esc to leave the cell's text; then, as in Jupyter: A / B add a cell above / below, M makes it a text cell, Y a code cell, D D deletes it, ↑ ↓ move between cells and Enter edits.

Python or R

Each notebook is either Python or R; the label at the top right says which, and whether the language has started (it starts in the background when a notebook of that language opens, and the first cell you run waits for it). All your Python notebooks share one Python, and all your R notebooks one R: a variable made in one Python notebook is there in the others.

  • Restart makes the language forget everything (variables, loaded packages) – then run the cells again from the top. Do that before you hand in or share a notebook: it shows that the notebook runs from start to end.
  • Stop (while code runs) stops it by restarting the language – its variables are forgotten.
  • Variables () lists what the language remembers now.

More on each language: Python · R.

Files and folders

A notebook's code runs in the notebook's own folder – ~/notebooks for most – so a file name without a folder means a file next to the notebook. Use full paths for files elsewhere: /data/examples/tables/yeast_genes.csv, or /home/user/… for your own (Python's open() does not understand ~; pandas and R do).

Files a cell writes appear in the Files tab and the terminal as soon as the cell has finished.

Terminal commands in a notebook

A cell whose first line is %%bash runs shell commands, with the programs of the terminal, in the notebook's folder – or in the folder %cd (Python) or setwd() (R) moved to. In Python a line can also start with !:

!samtools faidx /data/examples/reads/reference.fa human_CYP2C19:11590-11640
%%bash
bcftools view -H /data/examples/variants/NA12878.calls.vcf.gz | cut -f 1-5 | head -3

Python notebooks also understand %pip install NAME, %cd, %pwd, %ls, %time, %who, %run script.py, and the cell commands %%writefile FILE, %%time, %%html and %%capture (what the cell prints is not shown – plots, tables and the output of ! commands still are; %%capture out keeps it in out: out.stdout is the text, out.show() shows it).

Saving and downloading

A notebook saves itself a moment after each change – the word next to its name says Editing…, then Saved; Ctrl+S saves at once. It is kept in this browser – see where your files are kept.

Download offers:

  • Jupyter notebook (.ipynb) – the notebook with its outputs and plots. It opens in Jupyter and JupyterLab, VS Code and Google Colab; an R notebook needs the R kernel there (IRkernel).
  • Python script (.py) or R script (.R) – the code alone.
  • Web page with the results (.html) – to read or print, without Jupyter.

Data files that the notebook reads are not inside it: download them too (Files tab), and keep them in the same folders relative to the notebook. %%bash cells need the same programs on the other computer.

Help with code

Ask AI on a cell explains the code, suggests improvements, or – after an error – explains the error and how to fix it, using the model you connected in the AI tab (The AI assistant). Without a model it explains common error messages by itself.

Your files

Python reads and writes your files: they are given to Python before each cell runs, and what it writes appears in the Files tab afterwards. The working folder is the notebook's folder (see Files and folders). /data/examples is read-only. Files larger than 300 MB are not passed to Python.

Data from the web

requests works with web services that allow requests from web pages – Ensembl, UniProt, NCBI E-utilities, EBI, the PDB and others (the Databases tab writes such code for you):

import requests

r = requests.get("https://rest.ensembl.org/lookup/symbol/homo_sapiens/CYP2C19",
                 headers={"Content-Type": "application/json"})
gene = r.json()
print(gene["id"], gene["seq_region_name"], gene["start"], gene["end"], gene["biotype"])

Sites that do not allow it (KEGG, most web pages) fail with a network error: download the file with your browser and upload it in the Files tab instead.

Python in the terminal

python script.py, python -c "…" and pip install NAME work in the terminal too, with the same Python as the notebooks (a script runs with its own variables). %run script.py runs a script inside a notebook.

Good to know

  • Python here runs on one processor core: no threads or multiprocessing, and no subprocess (use ! or %%bash for programs).
  • Memory is limited to a few gigabytes. Work on samples of very large files, or summarise them in the terminal first.
  • A long computation can be stopped with Stop; that restarts Python, so its variables are forgotten.
  • input() does not work in a notebook: put the values in a variable instead.

Differential expression: DESeq2 and edgeR

The example counts are a real RNA-seq experiment: four cell lines of airway smooth muscle, each with and without the steroid dexamethasone. The first library(DESeq2) downloads about 40 packages – a minute; DESeq() on 22,000 genes takes another.

library(DESeq2)
counts <- as.matrix(read.delim("/data/examples/rnaseq/airway_counts.tsv", row.names = 1, check.names = FALSE))
samples <- read.delim("/data/examples/rnaseq/airway_samples.tsv", row.names = 1)
samples$cell <- factor(samples$cell)
samples$dex <- factor(samples$dex, levels = c("untrt", "trt"))
dds <- DESeqDataSetFromMatrix(counts, samples, design = ~ cell + dex)
dds <- DESeq(dds[rowSums(counts(dds)) >= 10, ])
res <- results(dds, contrast = c("dex", "trt", "untrt"), alpha = 0.05)
summary(res)

Good to know

  • There are no background jobs (&), no sudo or apt: nothing can be installed in the terminal except Python packages (pip install).

  • curl and wget reach web services that allow web pages to use them (EBI, UniProt, Ensembl, NCBI…), not every site. See What is different in the browser.

Reads: quality, trimming, simulation

FASTQ files hold reads with a quality for every base. fastp checks and trims them, cutadapt finds and removes adapters and primers, seqtk does many small jobs, wgsim makes simulated reads from a reference.

The examples work in a folder of your own:

A look at the reads

head -8 /data/examples/reads/NA12878_R1.fastq
seqtk fqchk /data/examples/reads/NA12878_R1.fastq | head -4

Each read is four lines: @name, the bases, +, and one quality letter per base (Phred+33: I = 40, 5 = 20, + = 10). seqtk fqchk summarises the bases and their qualities.

fastp: quality control and trimming

fastp -i /data/examples/reads/NA12878_R1.fastq -I /data/examples/reads/NA12878_R2.fastq \
      -o trimmed_R1.fastq -O trimmed_R2.fastq \
      --detect_adapter_for_pe --cut_tail -q 20 -l 50 \
      -h fastp.html -j fastp.json
open fastp.html

With these options fastp removes adapters, trims low-quality bases from the 3′ ends (--cut_tail), and drops reads with too many bad bases or fewer than 50 bases left; the two output files stay in step (read for read). Without --cut_tail or --cut_front fastp trims no ends: it removes adapters and drops poor reads. The HTML report shows quality, GC content and duplication before and after; fastp.json has the same numbers for a script (jq .summary fastp.json).

cutadapt: adapters, primers and quality

When a DNA fragment is shorter than the read, the sequencer reads on into the adapter at the end of the fragment. /data/examples/trimming/ has 384 read pairs of a yeast RNA-seq run that were chosen because many of them do: Cutadapt looks for the adapter you give it in every read and cuts it off, with everything after it.

cutadapt -a AGATCGGAAGAGCACACGTCTGAACTCCAGTCA -A AGATCGGAAGAGCGTCGTGTAGGGAAAGAGTGT \
         -o trimmed_1.fastq -p trimmed_2.fastq \
         /data/examples/trimming/SRR6357070_adapters_1.fastq /data/examples/trimming/SRR6357070_adapters_2.fastq > cutadapt_report.txt
head -20 cutadapt_report.txt

The report says that 205 of the 384 first reads, and 209 of the second, had the adapter, and how many bases went. Mapping reads

Mapping finds where each read comes from in a reference sequence. minimap2, Bowtie 2, BWA and BWA-MEM2 map DNA reads, HISAT2 maps RNA-seq reads across introns; samtools sorts, indexes, filters and counts the alignments, and mosdepth measures the depth.

The examples work in a folder of your own:

The reference

The example reference has two pieces of human chromosome 10 (GRCh37), named human_CYP2C19 and human_CYP2C9. samtools faidx indexes a FASTA file and cuts regions out of it:

cp /data/examples/reads/reference.fa .
samtools faidx reference.fa
cut -f 1,2 reference.fa.fai
samtools faidx reference.fa human_CYP2C19:11590-11640

minimap2

minimap2 -ax sr reference.fa /data/examples/reads/NA12878_R1.fastq /data/examples/reads/NA12878_R2.fastq > mapped.sam
samtools sort -o mapped.bam mapped.sam
samtools index mapped.bam
samtools flagstat mapped.bam

-ax sr is the preset for short paired reads (map-ont and map-pb for long reads, asm5 for an assembly against a reference). The two steps can be one pipe: minimap2 -ax sr … | samtools sort -o mapped.bam -. A read group names the sample in the BAM file – variant callers use it: -R '@RG\tID:NA12878\tSM:NA12878'.

Bowtie 2

cat bowtie2.log

bowtie2-build makes the index (six .bt2 files) once. The summary of the mapping goes to the standard error – here into bowtie2.log. Presets: --very-fast … --very-sensitive, and --local for local alignment.

BWA

bwa index makes the index once: five files (.amb .ann .bwt .pac .sa) next to the FASTA file – so the FASTA file must be in a folder of your own, not in the read-only examples. bwa mem is BWA's aligner for reads of 70 bases and more; it reads .fastq.gz files too. Its messages go to the standard error (here bwa.log); the CPU times in them are not measured in the browser – the real times are.

BWA-MEM2

bwa-mem2 index reference.fa > /dev/null 2>&1
bwa-mem2 mem -R '@RG\tID:NA12878\tSM:NA12878' reference.fa /data/examples/reads/NA12878_R1.fastq /data/examples/reads/NA12878_R2.fastq 2> bwamem2.log | samtools sort -o bwamem2.bam -

BWA-MEM2 is bwa mem's algorithm, rewritten to use the vector instructions of modern processors: on a server it maps several times faster than BWA, with the same alignments as bwa mem 0.7.17. It needs an index of its own – bwa-mem2 index writes .0123 .amb .ann .bwt.2bit.64 .pac; one made by bwa index does not do. In the browser it is not faster than BWA, and it takes a few hundred MB of memory even for a small reference. Compare the two: samtools view bwa.bam | cut -f 1-6 | head and the same for bwamem2.bam.

HISAT2, for RNA-seq reads

A read from a spliced RNA can span an intron: its first part matches one exon, the rest the next. HISAT2 splits such reads across the intron. The example reads are 256 pairs of yeast RNA-seq reads; the reference is chromosome I of yeast.

hisat2-build /data/examples/rnaseq/yeast_chrI.fa yeast_chrI > /dev/null 2>&1
hisat2 -x yeast_chrI -1 /data/examples/rnaseq/SRR6357070_1.fastq -2 /data/examples/rnaseq/SRR6357070_2.fastq 2> hisat2.log | samtools sort -o rnaseq.bam -
samtools index rnaseq.bam
cat hisat2.log
samtools view rnaseq.bam | awk '$6 ~ /N/ {print $3, $4, $6}' | head -3

hisat2-build writes eight .ht2 files; -x names them without the ending. A spliced read has an N in its CIGAR string: 94M113N7M is 94 bases on the genome, an intron of 113 bases skipped, then 7 more. Known introns can help: --known-splicesite-infile /data/examples/rnaseq/yeast_chrI.splice_sites.tsv; for DNA reads use --no-spliced-alignment. hisat2 unpacks .gz read files first, as its wrapper script does; --un and --al (also done by the wrapper) are not available – samtools fastq -f 4 gets the unmapped reads. The RNA-seq recipe goes on to differential expression.

Depth with mosdepth

samtools depth prints a line for every position; mosdepth summarises the depth of a whole BAM file at once – per sequence, in windows, or in the regions of a BED file – and writes compressed BED files that the genome browser can show. It needs the index of the BAM file (samtools index).

mosdepth cyp2c mapped.bam
cat cyp2c.mosdepth.summary.txt
mosdepth -n --by /data/examples/annotation/cyp2c_exons.bed --thresholds 1,10,20 exons mapped.bam
zcat exons.regions.bed.gz | head -5
zcat exons.thresholds.bed.gz | head -5

The summary has the length of each sequence, the bases covered by reads, and the mean, smallest and largest depth. cyp2c.mosdepth.global.dist.txt tells which share of the bases has at least each depth – the usual "90% of the exome at 20×". -n leaves out the per-base file; --by 1000 gives windows of 1000 bases instead of a BED file; -Q 20 counts only reads with a mapping quality of 20 or more. mosdepth keeps an array as long as the longest sequence in the BAM file: yeast chromosomes and the example slices are fine, a whole human chromosome is too big for a browser.

SAM flags

The second column of a SAM line is a sum of bits: 1 paired, 2 properly paired, 4 unmapped, 16 reverse strand, 256 secondary, 1024 duplicate, 2048 supplementary. -f keeps reads that have all the given bits, -F drops reads that have any of them.

RNA-seq: counts and abundances

After mapping, RNA-seq reads are counted. featureCounts counts the reads that fall in each gene; StringTie assembles the transcripts that the alignments show and estimates their abundance. kallisto and Salmon need no alignments to the genome: they estimate the abundance of each transcript from the reads and the transcript sequences.

The examples use the 256 pairs of yeast RNA-seq reads and chromosome I of yeast, and work in a folder of their own:

The alignments

featureCounts and StringTie work on a BAM file sorted by position. --dta makes HISAT2 report alignments for transcript assembly (it wants longer anchors across introns, as StringTie does).

hisat2-build /data/examples/rnaseq/yeast_chrI.fa yeast_chrI > /dev/null 2>&1
hisat2 --dta -x yeast_chrI -1 /data/examples/rnaseq/SRR6357070_1.fastq -2 /data/examples/rnaseq/SRR6357070_2.fastq 2> hisat2.log | samtools sort -o rnaseq.bam -
samtools index rnaseq.bam

featureCounts: reads per gene

featureCounts -p --countReadPairs -a /data/examples/rnaseq/yeast_chrI.gtf -o counts.txt rnaseq.bam 2> featurecounts.log
cat counts.txt.summary | awk '$2 > 0'
tail -n +3 counts.txt | sort -k7,7nr | head -5 | cut -f 1,6,7

counts.txt has a line per gene: its ID, where its exons are, its length and the count – a column for each BAM file, so featureCounts … -o counts.txt s1.bam s2.bam s3.bam makes the table of a whole experiment, the input of DESeq2 or edgeR. The summary says why reads were not counted: Unassigned_NoFeatures (no gene there), Unassigned_Ambiguity (more than one gene), Unassigned_MultiMapping (the read maps to several places; -M counts it anyway). Its report goes to the standard error – here featurecounts.log.

  • -p --countReadPairs: the reads are pairs, and each pair (each fragment) counts once. featureCounts 2.1 stops with "Paired-end reads were detected in single-end read library" if -p is missing for paired reads.
  • -s 1 or -s 2: a stranded library, where the reads come from one strand of the RNA. Most RNA-seq kits today are reverse-stranded (-s 2); Salmon tells which (below).
  • -t exon -g gene_id (the defaults): count over the exons, and add them up by gene. -f counts each exon by itself.

featureCounts counts on several threads – -T 2 to -T 4 here; one if not asked for more. That needs a cross-origin isolated page, which the workbench makes its page when it starts – see programs on several threads.

StringTie: transcripts and their abundance

stringtie rnaseq.bam -G /data/examples/rnaseq/yeast_chrI.gtf -o stringtie.gtf -A gene_abundance.tsv
awk '$3 == "transcript"' stringtie.gtf | wc -l
sort -t $'\t' -k9,9gr gene_abundance.tsv | head -5 | cut -f 1,2,7-9

StringTie builds the transcripts that the reads show, guided by the annotation (-G). Each is called STRG.N.M; one that matches an annotated transcript names it (reference_id, ref_gene_name). For each it gives the coverage, FPKM and TPM (in the GTF file); -A writes a table per gene. -e leaves out new transcripts and only estimates the known ones; -B adds the tables that the R package Ballgown reads. Assemblies of several samples are joined with stringtie --merge -G genes.gtf -o merged.gtf s1.gtf s2.gtf.

kallisto and Salmon: abundances without a BAM file

Both need the sequences of the transcripts. gffread cuts them out of the genome, as the annotation describes them:

gffread -w transcripts.fa -g /data/examples/rnaseq/yeast_chrI.fa /data/examples/rnaseq/yeast_chrI.gtf
grep -c '>' transcripts.fa

kallisto finds, for each read pair, which transcripts it could come from (pseudoalignment: compatible k-mers, no base-by-base alignment), and shares the reads out among the transcripts with an EM algorithm:

kallisto index -i transcripts.idx transcripts.fa > /dev/null 2>&1
kallisto quant -i transcripts.idx -o kallisto_out /data/examples/rnaseq/SRR6357070_1.fastq /data/examples/rnaseq/SRR6357070_2.fastq 2> kallisto.log
sort -t $'\t' -k4,4gr kallisto_out/abundance.tsv | head -5

Salmon maps the reads to the transcripts (selective alignment), learns the lengths of the fragments and the strand of the reads, and shares the reads out among the transcripts:

salmon index -t transcripts.fa -i salmon_index > /dev/null 2>&1
salmon quant -i salmon_index -l A -1 /data/examples/rnaseq/SRR6357070_1.fastq -2 /data/examples/rnaseq/SRR6357070_2.fastq -o salmon_out 2> salmon.log
sort -t $'\t' -k5,5gr salmon_out/quant.sf | head -5
grep expected_format salmon_out/lib_format_counts.json

abundance.tsv (kallisto) and quant.sf (Salmon) give for each transcript its length, its effective length, the estimated number of reads (est_counts, NumReads) and TPM. -l A lets Salmon find out how the library was made: here ISR – inward pairs, read 1 from the reverse strand. That is a reverse-stranded library: featureCounts -s 2, stringtie --rf, kallisto quant --rf-stranded. Try the counts with -s 2, and with -s 1.

Do the four agree? Join the counts of the genes – yeast genes here have one transcript each, named like the gene:

tail -n +3 counts.txt | cut -f 1,7 | sort > fc.tsv
tail -n +2 kallisto_out/abundance.tsv | cut -f 1,4 | sort > kallisto.tsv
tail -n +2 salmon_out/quant.sf | cut -f 1,5 | sort > salmon.tsv
join fc.tsv kallisto.tsv | join - salmon.tsv | sort -k2,2nr | head -8
Good to know
  • Counts are what DESeq2 and edgeR need: featureCounts' table as it is; for kallisto and Salmon, R's tximport sums the transcripts of each gene. TPM is for comparing genes within a sample, not for testing.
  • Indexes belong to the program that made them: bwa index, hisat2-build, kallisto index and salmon index each make their own. An index that Salmon made on a 64-bit computer cannot be read here, nor one made here there.
  • With thousands of reads the numbers here are an exercise, not biology: real samples have millions.
  • Reads of single cells carry a cell barcode and a UMI as well: kallisto bus and bustools count them per cell – see Single-cell RNA-seq.

Single-cell RNA-seq: bustools

In single-cell RNA-seq each cell is in a droplet of its own, and every read carries two tags: the barcode of its droplet – its cell – and a UMI, the tag of the RNA molecule it was copied from. kallisto bus pseudoaligns the reads and writes what each one says as a BUS record. bustools sorts the records, corrects the barcodes and counts the molecules of each gene in each cell.

The examples work in a folder of your own:

The reads and the BUS file

/data/examples/singlecell/ has data of mouse cells, prepared with 10x Chromium v2 (SRA run SRR8599150): 2,500 of its read pairs, and a small BUS file that kallisto bus wrote for reads of the experiment, with the files of the reference it used.

head -2 /data/examples/singlecell/R1.fastq
head -2 /data/examples/singlecell/R2.fastq
bustools inspect /data/examples/singlecell/input.bus

Read 1 has 26 bases: the cell's barcode (16) and the UMI (10). Read 2, 98 bases, is the cDNA – the part that says which transcript the molecule came from. kallisto bus (kallisto bus -i INDEX -o DIR -x 10xv2 R1.fastq R2.fastq) needs an index of the mouse transcriptome, which is too big for the browser; input.bus is what it wrote. Each record holds a barcode, a UMI, an equivalence class – the set of transcripts the read fits, numbered as in matrix.ec – and how many reads said exactly that:

bustools text -p /data/examples/singlecell/input.bus | head -5
head -3 /data/examples/singlecell/matrix.ec
head -3 /data/examples/singlecell/transcripts.txt

A line of matrix.ec is an equivalence class and its transcripts, by their line in transcripts.txt (counted from 0).

Sort, correct, sort again

bustools sort -o sorted.bus /data/examples/singlecell/input.bus
bustools correct -w /data/examples/singlecell/whitelist.txt -o corrected.bus sorted.bus
bustools sort -o corrected.sorted.bus corrected.bus

Sorting puts the records of the same barcode and UMI together, and merges those that are the same (34 records become 31). correct compares each barcode with the list of the technology – 10x v2 has 737,280 barcodes, and whitelist.txt holds those near the barcodes of this file: a barcode in the list stays (28 records), one that is a single letter from exactly one barcode of the list takes that barcode (1), and the rest are left out (2) – sequencing errors, or droplets that were not made by the kit. Correction changes barcodes, so the records are sorted again.

Count: a matrix of cells and genes

mkdir -p counts
bustools count --genecounts -g /data/examples/singlecell/transcripts-to-genes.txt -e /data/examples/singlecell/matrix.ec \
    -t /data/examples/singlecell/transcripts.txt -o counts/cells_x_genes corrected.sorted.bus
ls counts
head -5 counts/cells_x_genes.mtx

count counts, for each barcode and each gene, the different UMIs – molecules, not reads: the copies of one molecule that PCR made count once. -g gives each transcript its gene, --genecounts counts genes rather than equivalence classes. The matrix is in Matrix Market format, which lists only what is not zero: after the header, its size – barcodes, genes, entries that are not zero – then one line per entry: the barcode's row, the gene's column, the count. cells_x_genes.barcodes.txt and cells_x_genes.genes.txt name the rows and the columns. Here each barcode has one molecule: 34 records are too few for more.

More cells, and which barcodes are cells

large/ holds 10,235 records of 358 barcodes of the same experiment, already corrected and sorted, with the files of their reference:

L=/data/examples/singlecell/large
bustools inspect -e $L/matrix.ec -w $L/whitelist.txt $L/input.bus | head -12
mkdir -p large_counts
bustools count --genecounts -g $L/transcripts-to-genes.txt -e $L/matrix.ec -t $L/transcripts.txt -o large_counts/cells_x_genes $L/input.bus
head -3 large_counts/cells_x_genes.mtx

358 barcodes, 3,733 genes. Most droplets hold no cell – only a little free RNA of the cells that broke – so most barcodes have very few molecules, and a few have many: those are the cells. Count the molecules of each barcode in Python, and draw them from the most to the fewest (a "knee plot"):

import os
import numpy as np
import scipy.io
import matplotlib.pyplot as plt

folder = os.path.expanduser("~/sc/large_counts")
m = scipy.io.mmread(f"{folder}/cells_x_genes.mtx").tocsr()
umis = np.asarray(m.sum(axis=1)).ravel()   # molecules per barcode
genes = np.asarray((m > 0).sum(axis=1)).ravel()   # genes seen per barcode
print(m.shape, "– molecules per barcode, the most first:", np.sort(umis)[::-1][:16].astype(int))
print("barcodes with 100 molecules or more:", (umis >= 100).sum(), "– median molecules per barcode:", np.median(umis))
plt.loglog(np.arange(1, len(umis) + 1), np.sort(umis)[::-1], marker=".", linestyle="none")
plt.xlabel("barcodes, by their molecules"); plt.ylabel("molecules (UMIs)")
plt.show()

Fourteen barcodes have 100 molecules or more – from 151 to 1,230 –, then the count falls to a few dozen and the median barcode has one: the cells, and then the empty droplets. Where the curve bends (the "knee") is where cells are told from empty droplets; tools such as DropletUtils (R) do this with statistics. These 358 barcodes are the first of the experiment's in alphabetical order, not a sample of it: they show how it is done, not what the experiment found.

More: bustools capture keeps (or, with -x, leaves out) the records of a list of transcripts or barcodes, bustools allowlist makes a barcode list from the data, bustools umicorrect corrects UMIs, bustools compress and decompress pack a BUS file; bustools COMMAND without arguments lists its options. In the browser bustools runs on one thread – sort -t N becomes -t 1, with a note – and sorts in 64 MB of memory unless told otherwise (1 GB at most: -m 4G becomes -m 64M).

The same steps are in the Galaxy tab: the tools bustools sort, correct, count, inspect and text (section Single-cell) – upload input.bus, whitelist.txt, matrix.ec, transcripts.txt and transcripts-to-genes.txt, then sort, correct, sort and count. They are the workbench’s own: Galaxy servers have no bustools tools and process single-cell reads with others (RNA STARsolo, Alevin). bustools is compiled to WebAssembly from its released source by the genomics-wasm project, and gives the same records and matrices as bustools built for Linux (see Programs and versions).

Variant calling

bcftools finds the positions where the reads differ from the reference, decides the genotypes, filters the calls and turns VCF files into tables. FreeBayes is a second caller, which looks at haplotypes rather than single positions. bgzip and tabix compress and index the VCF files.

The examples work in a folder of your own:

From a BAM file to variants

First a sorted BAM file (see Mapping reads):

minimap2 -ax sr -R '@RG\tID:NA12878\tSM:NA12878' /data/examples/reads/reference.fa \
    /data/examples/reads/NA12878_R1.fastq /data/examples/reads/NA12878_R2.fastq 2> /dev/null \
  | samtools sort -o mapped.bam -
samtools index mapped.bam

Then the two steps of bcftools: mpileup collects the evidence at each position, call decides the genotypes:

bcftools mpileup -f /data/examples/reads/reference.fa mapped.bam | bcftools call -mv -Oz -o calls.vcf.gz
bcftools index calls.vcf.gz
bcftools view -H calls.vcf.gz | cut -f 1-6 | head

-m is the multiallelic caller, -v keeps only variant sites, -Oz writes compressed VCF (-Ov plain VCF, -Ob BCF).

Filter and count

bcftools filter -i 'QUAL>=20 && INFO/DP>=5' -Oz -o filtered.vcf.gz calls.vcf.gz
bcftools index filtered.vcf.gz
bcftools view -H filtered.vcf.gz | wc -l
bcftools view -H -v snps filtered.vcf.gz | wc -l
bcftools view -H -v indels filtered.vcf.gz | wc -l
bcftools stats filtered.vcf.gz | grep -E "^SN|^TSTV"

The expression language: QUAL, INFO/DP, FORMAT/GT="1/1", TYPE="snp", with &&, ||. -e excludes instead of including.

A table of the calls

bcftools query -H -f '%CHROM\t%POS\t%REF\t%ALT\t%QUAL\t%INFO/DP[\t%GT]\n' filtered.vcf.gz > calls.tsv
head calls.tsv

A table like this reads straight into pandas or R (pd.read_csv("calls.tsv", sep="\t")). A known position, such as the CYP2C19*2 variant (rs4244285, G>A) at position 11,616 of human_CYP2C19 – NA12878 carries it on one chromosome (0/1):

bcftools view -H -r human_CYP2C19:11616 filtered.vcf.gz | cut -f 1-10

FreeBayes

FreeBayes reads the same sorted BAM file and the reference (which needs its .fai index – samtools faidx; FreeBayes makes one if it is missing) and writes a VCF file:

freebayes -f /data/examples/reads/reference.fa mapped.bam > freebayes.vcf
bcftools view -H freebayes.vcf | wc -l
bcftools filter -i 'QUAL>=20' -Oz -o freebayes.filtered.vcf.gz freebayes.vcf
bcftools index freebayes.filtered.vcf.gz
bcftools view -H -r human_CYP2C19:11616 freebayes.filtered.vcf.gz | cut -f 1-6

FreeBayes also writes the sites it considered and does not believe – QUAL near 0, genotype 0/0 – so filter on QUAL. Its INFO fields differ from bcftools': DP depth, RO and AO the reads with the reference and the other allele, TYPE snp, mnp, ins, del or complex. Useful options: -r human_CYP2C19:11000-12500 (one region; needs the BAM index), -p 1 (a haploid organism), -C 3 (at least three reads for an allele), --min-mapping-quality 20. Which calls do the two callers share?

bcftools isec -n=2 -w1 filtered.vcf.gz freebayes.filtered.vcf.gz | grep -vc "^#"
bcftools isec -C -w1 filtered.vcf.gz freebayes.filtered.vcf.gz | grep -v "^#" | cut -f 1-5

-n=2 keeps the sites in both files, -C the sites of the first file only. Positions where the callers disagree are worth a look in the genome browser.

bgzip and tabix

A VCF file that tools read by region must be compressed with bgzip (not plain gzip) and indexed:

bcftools view filtered.vcf.gz > plain.vcf
bgzip -c plain.vcf > again.vcf.gz
tabix -p vcf again.vcf.gz
tabix again.vcf.gz human_CYP2C19:11000-12000 | cut -f 1-5

Also useful: bcftools norm (normalise indels against the reference), bcftools isec (compare two call sets), bcftools annotate. bcftools COMMAND --help lists the options of a command. The plugins (bcftools +NAME) cannot run in a browser.

igv filtered.vcf.gz mapped.bam shows the calls next to the reads in the Genome browser.

Variants of a tumour that its matched normal sample does not have – somatic variants – need callers that compare the two: see Somatic variants. One of them, lofreq call, also calls the variants of a single sample at low frequencies, as in a virus population.

Somatic variants: tumour and normal

A somatic variant is one that the tumour has and the rest of the body does not. The callers here compare the reads of a tumour with the reads of a matched normal sample of the same person: SomaticSniper, LoFreq (lofreq somatic) and Strelka2.

The examples work in a folder of your own:

The example data

/data/examples/somatic/ holds real reads of the breast-cancer cell line HCC1395 (tumor.bam) and of HCC1395BL, a cell line made from the blood of the same donor (normal.bam). They come from the SEQC2 consortium, which sequenced the two cell lines many times over and published the somatic variants it is confident of. To keep them small, the reads are those of two windows of chromosome 21 (GRCh38), and the windows are the reference: chr21_10572001_10582000 (10 kb) and chr21_21404501_21423500 (19 kb). A position plus 10,572,000 – or plus 21,404,500 – is the position on chromosome 21.

ls /data/examples/somatic/
samtools view -H /data/examples/somatic/tumor.bam | grep -E "^@(SQ|RG)"
grep -v "^##" /data/examples/somatic/truth.vcf | cut -f 1-7

truth.vcf has the four SEQC2 variants in these windows: two SNVs and two deletions of one base. The SNV at chr21_21404501_21423500:14045 is a rare one (about 7 % of the tumour cells): in this particular set of reads no read shows it, and no caller can find it. The BAM files are sorted and indexed, and both name the two windows – the callers check that tumour, normal and reference agree.

Look at the first SNV yourself, tumour and normal together:

igv --genome /data/examples/somatic/reference.fa /data/examples/somatic/tumor.bam /data/examples/somatic/normal.bam --locus chr21_10572001_10582000:4,659-4,699

About a quarter of the tumour's reads have a G at position 4,679; none of the normal's do. That is what a somatic SNV looks like. (A germline variant would be in both, at about half or all of the reads.)

SomaticSniper

bam-somaticsniper -F vcf -f /data/examples/somatic/reference.fa \
    /data/examples/somatic/tumor.bam /data/examples/somatic/normal.bam somaticsniper.vcf
grep -v "^##" somaticsniper.vcf | cut -f 1,2,4,5,9-11

The tumour BAM comes first, then the normal, then the output file. Each line has the two samples, NORMAL then TUMOR, in the fields that FORMAT names. Two of them matter most: SS, the somatic status (0 wild type, 1 germline, 2 somatic, 3 loss of heterozygosity – LOH, 5 unknown), and SSC, the somatic score (higher is surer). Only the first call, the true SNV, has a high SSC; the others are LOH calls and weak candidates. To keep the somatic calls with a score of 40 or more:

bam-somaticsniper -F vcf -Q 40 -L -G -f /data/examples/somatic/reference.fa \
    /data/examples/somatic/tumor.bam /data/examples/somatic/normal.bam somaticsniper.strict.vcf
grep -v "^#" somaticsniper.strict.vcf | cut -f 1,2,4,5

-Q is the lowest somatic score reported, -L leaves out LOH calls, -G gains of reference. SomaticSniper calls SNVs only. -n and -t name the normal and tumour samples in the VCF – -t is not a number of threads.

LoFreq: lofreq somatic

LoFreq calls variants at any frequency the reads support. lofreq somatic calls the normal and the tumour, and keeps the tumour's calls that the normal does not have. For indels LoFreq needs indel qualities in the reads (lofreq indelqual); then the BAM files must be indexed again:

lofreq indelqual --dindel -f /data/examples/somatic/reference.fa -o tumor.iq.bam /data/examples/somatic/tumor.bam
lofreq indelqual --dindel -f /data/examples/somatic/reference.fa -o normal.iq.bam /data/examples/somatic/normal.bam
samtools index tumor.iq.bam && samtools index normal.iq.bam
lofreq somatic -n normal.iq.bam -t tumor.iq.bam -f /data/examples/somatic/reference.fa --call-indels -o lofreq_
ls lofreq_*
zcat lofreq_somatic_final.snvs.vcf.gz | grep -v "^##"
zcat lofreq_somatic_final.indels.vcf.gz | grep -v "^##"

Everything starts with the prefix given with -o. lofreq_somatic_final.snvs.vcf.gz and …indels.vcf.gz are the results; the other files are the steps on the way (relaxed and stringent calls of each sample, and the raw somatic calls). INFO has the allele frequency in the tumour (AF), the depth (DP) and a strand-bias score (SB). On the example LoFreq finds the SNV and both deletions. It warns that no dbSNP file was given: with human data, -d dbsnp.vcf.gz removes known germline variants. LoFreq's authors call this workflow experimental. lofreq call -f REF.fa -o calls.vcf sample.bam calls the variants of one sample, at low frequencies too.

Strelka2

Strelka2 is used in two steps, as on any computer. The first configures a run in a folder of its own and checks the input; the second runs it:

configureStrelkaSomaticWorkflow.py --normalBam /data/examples/somatic/normal.bam --tumorBam /data/examples/somatic/tumor.bam \
    --referenceFasta /data/examples/somatic/reference.fa --runDir strelka_run
strelka_run/runWorkflow.py -m local -j 1
ls strelka_run/results/variants/
bcftools view -H strelka_run/results/variants/somatic.snvs.vcf.gz | cut -f 1-7
bcftools view -H -f PASS strelka_run/results/variants/somatic.indels.vcf.gz | cut -f 1-7

Strelka writes every candidate it scored, and marks in FILTER whether it passed: PASS, or the filters it failed (LowEVS, a low empirical variant score; LowDepth). bcftools view -f PASS keeps the passing calls: here the SNV and both deletions. The normal and tumour columns hold the counts of each base (AU, CU, GU, TU) and, for indels, of reads with and without the indel (TAR, TIR); QSS and QSI are the somatic qualities. strelka_run/results/stats/runStats.tsv summarises the run.

Options of the first step: --exome (exome or panel data: no filter for unusually high depth), --callRegions regions.bed.gz (call only in these regions – compressed with bgzip and indexed with tabix -p bed; /data/examples/somatic/regions.bed.gz is one), --region chr:start-end, --outputCallableRegions; --allHelp lists them all. Each run needs a new folder. Strelka's workflow scripts are Python 2, which is not here: the terminal runs them itself, with Strelka's own programs. -j does not matter (the tasks run one after another), and there is no sge mode.

Compare the callers with the truth

grep -v "^#" /data/examples/somatic/truth.vcf | cut -f 1,2,4,5 > truth.tsv
grep -v "^#" somaticsniper.strict.vcf | cut -f 1,2,4,5 > sniper.tsv
zcat lofreq_somatic_final.snvs.vcf.gz lofreq_somatic_final.indels.vcf.gz | grep -v "^#" | cut -f 1,2,4,5 > lofreq.tsv
bcftools view -H -f PASS strelka_run/results/variants/somatic.snvs.vcf.gz | cut -f 1,2,4,5 > strelka.tsv
bcftools view -H -f PASS strelka_run/results/variants/somatic.indels.vcf.gz | cut -f 1,2,4,5 >> strelka.tsv
for f in sniper lofreq strelka; do echo "$f: $(grep -c -F -x -f truth.tsv $f.tsv) of $(wc -l < truth.tsv) true variants, $(wc -l < $f.tsv) calls"; done

Two windows chosen around known variants are no benchmark – they show how the callers report, not how good they are. Real data needs more: a panel of normals, known germline variants, a look at each candidate in the genome browser.

Metagenomics: who is in the sample

The DNA of a sample of soil, gut or water comes from many organisms at once. Kraken2 gives each read the taxon – species, genus, family … – whose DNA it matches in a database of known genomes. Bracken then estimates how many reads each species has, including the reads that Kraken2 could place only on a genus or a family.

The examples work in a folder of your own:

The example data

/data/examples/metagenomics/ holds 4,096 pairs of real Illumina reads of a mock community: a mixture made to a known recipe, the ZymoBIOMICS Microbial Community DNA Standard – the DNA of eight bacteria, 12 % each, and of two yeasts, 2 % each. Because the answer is known, a mock community shows what a method gets right and what it gets wrong. db/ is a small Kraken2 database: the first million bases of three bacterial chromosomes – Escherichia coli, Salmonella enterica and Shigella flexneri – with their taxonomy.

ls /data/examples/metagenomics/ /data/examples/metagenomics/db/
zcat /data/examples/metagenomics/reads_1.fastq.gz | head -4
cat /data/examples/metagenomics/db/seqid2taxid.map

E. coli and Salmonella are in the community; Shigella is not – it is there as a close relative of E. coli. The other six bacteria and the yeasts are not in the database at all. seqid2taxid.map gives each sequence of the database its NCBI taxonomy ID: 562 is E. coli, 28901 S. enterica, 623 S. flexneri.

Kraken2: a taxon for every read

kraken2 --db /data/examples/metagenomics/db --paired --report sample.report --output sample.kraken \
    /data/examples/metagenomics/reads_1.fastq.gz /data/examples/metagenomics/reads_2.fastq.gz
head -5 sample.kraken

Kraken2 cuts each read into k-mers (31-base minimizers of 35-base windows, here) and looks them up in the database, which knows for each one the taxon it belongs to – the species, or, for a k-mer that several species share, their common ancestor. It puts the read on the taxon whose path from the root collects most of its k-mers. With --paired the two reads of a pair are classified together, so the 4,096 "sequences" are read pairs: 231 are classified, 3,865 are not.

A line of sample.kraken: C or U (classified or not), the name of the read, the taxonomy ID it was given (0: none), the lengths of the two reads, and its k-mers – 562:113 are 113 k-mers of taxon 562, 0:4 four k-mers that are not in the database, and |:| separates the first read from the second. A read of 151 bases has 117 k-mers of 35.

The report

cat sample.report

One line per taxon: the percentage of all reads in its clade (the taxon and everything below it), the reads in the clade, the reads given to this taxon itself, its rank (U unclassified, R root, D domain, K kingdom, P phylum, C class, O order, F family, G genus, S species; R1, S1 … are ranks in between), its taxonomy ID and its name, indented by depth. This report is what Bracken reads.

  • Most reads are unclassified. Only E. coli and Salmonella of the community are in the database, and only a fifth of their genomes (one megabase each). They are 24 % of the DNA, so about 5 % of the reads can be classified – and Kraken2 classifies 5.6 %. Kraken2 can find only what its database holds: a read of an organism that is not there stays unclassified, or goes to the nearest relative that is.
  • 31 reads stop at the family, Enterobacteriaceae: their k-mers are shared by species of different genera, and Kraken2 does not guess between them.
  • 9 reads go to Shigella flexneri, which is not in the community. Shigella is E. coli in all but name – the Shigella species are lineages within E. coli – and these are E. coli reads with k-mers that, of these three genomes, only Shigella's has. A database with hundreds of E. coli genomes would put most of them on E. coli. A name in a Kraken2 report is a hypothesis, not proof.

What the database knows decides all of this. kraken2-inspect shows how its minimizers are shared out:

kraken2-inspect --db /data/examples/metagenomics/db

A quarter of them belong to the family only – mostly what E. coli and Shigella have in common. Salmonella has 42 % to itself, E. coli and Shigella 18 % and 16 %: a read from the part of E. coli that Shigella shares can say no more than "Enterobacteriaceae".

Bracken: how much of each species

Bracken takes the reads that Kraken2 left on a genus or a family and shares them out among the species below, in proportion to how often each species gives reads that end there. It knows that from the database: database151mers.kmer_distrib, made by bracken-build for reads of 151 bases – the reads' length, which you give with -r.

bracken -d /data/examples/metagenomics/db -i sample.report -o sample.bracken -r 151 -l S -t 10
cat sample.bracken

-l S asks for species (G for genera, F for families …), and -t 10 leaves out species with fewer than 10 reads of their own. The table has, per species, Kraken2's reads, the reads added, the new estimate and its share of all the estimates. E. coli gets 30 of the 31 family reads – Salmonella's reads seldom end at the family, E. coli's often do, because of Shigella. Shigella, with 9 reads, is below the threshold and is left out. The two species of the community that the database holds come out at 45 % and 55 %; in the standard they are equal. With -t 1 every species counts:

bracken -d /data/examples/metagenomics/db -i sample.report -o sample_t1.bracken -r 151 -l S -t 1
cat sample_t1.bracken
cat sample_bracken_species.report

Now Shigella has 11 reads – a species that is not in the sample. The threshold is a guard against such names; it cannot tell a true rare species from a false one. Bracken also writes a report in Kraken2's format with the new counts (-w names it; by default it is the report's name with _bracken_species), which shows only the classified reads: the percentages there are of those, not of all reads.

Your own database

A Kraken2 database is built from three things: the sequences, in library/ (FASTA files ending in .fna); seqid2taxid.map, the taxonomy ID of each sequence; and taxonomy/ with NCBI's nodes.dmp (each taxon's parent and rank) and names.dmp (the names). The example has all three. Copy it, remove what was built from it, and build it again:

cp -r /data/examples/metagenomics/db ~/mydb
rm ~/mydb/*.k2d ~/mydb/*.kmer_distrib
ls -R ~/mydb
kraken2-build --build --db ~/mydb
kraken2-inspect --db ~/mydb --skip-counts
cmp ~/mydb/hash.k2d /data/examples/metagenomics/db/hash.k2d && echo "the same hash table"

kraken2-build --build estimates the size of the hash table, then fills it: hash.k2d (the minimizers and their taxa), taxo.k2d (the taxonomy) and opts.k2d (the settings: --kmer-len, --minimizer-len …). Then Bracken's distribution for reads of 151 bases:

bracken-build -d ~/mydb -t 1 -k 35 -l 151
cmp ~/mydb/database151mers.kmer_distrib /data/examples/metagenomics/db/database151mers.kmer_distrib && echo "the same distribution"

bracken-build classifies the database's own sequences with Kraken2 (database.kraken, kept for the next read length), cuts them into every possible read of the length given with -l, and counts where the reads of each genome end. -k is the database's k-mer length (35, Kraken2's default). Make one distribution for each read length you have.

On a computer, databases for real samples are made with kraken2-build --standard or --download-library, which download genomes and NCBI's taxonomy – tens of gigabytes for the standard database – or downloaded ready-made; Galaxy servers have them installed. Neither is possible in the browser, which holds a few hundred megabytes at most. Here you can build small databases of your own sequences: put them in library/, write seqid2taxid.map, and take the lineages from NCBI's taxonomy into nodes.dmp and names.dmp.

Options worth knowing

--confidence 0.1: a read is placed only where at least that share of its k-mers agrees – it moves up the tree, or stays unclassified (default 0). --minimum-hit-groups 3 asks for more evidence before a call (default 2). --use-names writes names in --output instead of numbers. --classified-out 'cl#.fq' --unclassified-out 'un#.fq' writes the reads themselves (the # becomes _1 and _2 for pairs) – the unclassified ones are what to look at next. --report-zero-counts lists every taxon of the database, --use-mpa-style writes the report in MetaPhlAn's format (d__Bacteria|k__Pseudomonadati|…). --output - writes no classifications. man kraken2, man bracken, kraken2-build --help and bracken -h have the rest.

In the browser Kraken2 and Bracken run on one thread (--threads and -t of bracken-build are left out, with a note), reads compressed with bzip2 cannot be read (gzip can), and nothing is downloaded. Bracken's two Python programs start a Python of their own for each command, which takes a few seconds.

Genes and protein domains: Prodigal and HMMER

A new bacterial genome is a long string of letters. Prodigal finds the genes in it that code for proteins. HMMER then compares proteins – or DNA – with profile HMMs: models of a whole family, built from an alignment of its members, which find relatives that a search with a single sequence can miss.

The examples work in a folder of your own:

Prodigal: the genes of a bacterium

/data/examples/bacteria/ has the first 60,000 bases of the chromosomes of Escherichia coli K-12 and Salmonella enterica Typhimurium, from NCBI RefSeq.

prodigal -i /data/examples/bacteria/ecoli.fna -o ecoli.gff -f gff -a ecoli.faa -d ecoli.ffn
head -5 ecoli.gff
grep -c '>' ecoli.faa

Prodigal first learns the genome – how rich in G and C its coding regions are, which start codons and ribosome binding sites it uses – and then finds its genes. It warns that it would like 100,000 bases or more to learn from; 60,000 are enough to see how it works. It finds 56 genes. A line of ecoli.gff is one gene: the sequence, the program, the type (CDS, coding sequence), start and end, a score, the strand, and in the last column what Prodigal knows about it – partial (10: it runs off the left end of the sequence), the start codon, the ribosome binding site (rbs_motif) and its confidence. Genotypes and association: PLINK 2

PLINK works with the genotypes of many people at once – thousands of people, millions of variants. It checks their quality, counts allele frequencies, measures linkage disequilibrium and relatedness, and tests each variant for association with a trait: a genome-wide association study, or GWAS. Every PLINK command has the same shape: the data (--vcf, --pfile, --bfile), filters, what to compute, and --out, the name of the files it writes.

The examples work in a folder of your own:

The data, and PLINK's own files

/data/examples/plink2/1kg-phase3-chr21.vcf.gz holds the genotypes of the 2,504 people of the 1000 Genomes Project (Phase 3) at the first 600 variants of chromosome 21 – real public data, and the test file of PLINK 2 itself. A VCF file has a column for each person:

zcat /data/examples/plink2/1kg-phase3-chr21.vcf.gz | grep -v '^##' | head -3 | cut -f 1-5,10-12
plink2 --vcf /data/examples/plink2/1kg-phase3-chr21.vcf.gz --make-pgen --out chr21
ls chr21.*

A genotype such as 0|1 gives the alleles of the two copies of the chromosome – 0 the reference allele (REF), 1 the alternative (ALT); | means phased: which copy carries which is known. --make-pgen writes PLINK 2's own files: chr21.pgen, the genotypes, packed tightly; chr21.pvar, the variants (the first columns of the VCF); chr21.psam, the people; and chr21.log, a record of what was done. --pfile chr21 reads the three back – much quicker than the VCF for every new command. PLINK 1's files, .bed, .bim and .fam, are still common: --make-bed writes them and --bfile reads them.

The log, and what PLINK prints, begin with the options in effect: besides yours, --threads 1 and --memory 640 require, which the terminal adds (see the end of this page).

Quality control: frequencies, missing genotypes, Hardy–Weinberg

plink2 --pfile chr21 --freq --missing --hardy --out qc
head -4 qc.afreq
awk 'NR > 1 && ($5 < 0.01 || $5 > 0.99)' qc.afreq | wc -l
tail -n +2 qc.hardy | sort -g -k10,10 | head -4

qc.afreq has the frequency of each ALT allele and the number of alleles counted – 5,008, two for each person. Most variants are rare: for 566 of the 600 the less common allele has a frequency below 1%, and hundreds were seen only once among the 5,008 chromosomes (a frequency of 0.0002). qc.smiss and qc.vmiss count the missing genotypes of each person and of each variant: none here, as the 1000 Genomes release gives every genotype – in data of your own, a person or a variant with many missing genotypes is a warning.

qc.hardy holds the Hardy–Weinberg exact test: are there as many heterozygotes as the allele frequency predicts? O(HET_A1) is the share of heterozygotes observed, E(HET_A1) the share expected, P the p-value. A few variants are very far from it, always with too many heterozygotes – 0.88 where 0.50 is expected. These variants lie on the short arm of chromosome 21, near its centromere, among repeated sequences – most likely, reads from two copies of a repeat were aligned to one place, and the difference between the copies looks like a heterozygous genotype in almost everyone. Such errors are what the Hardy–Weinberg filter is for.

Filters

plink2 --pfile chr21 --maf 0.01 --hwe 1e-6 --make-pgen --out chr21_qc

Filters act before anything else. --maf 0.01 keeps the variants whose minor allele frequency is 1% or more; --hwe 1e-6 removes those with a Hardy–Weinberg p-value below 10−6; --geno 0.02 would remove variants with more than 2% of their genotypes missing, and --mind 0.02 such people. The log says what each did: 25 variants removed by --hwe (all with too many heterozygotes), 566 by --maf, 9 remaining. --keep FILE and --remove FILE choose people by their IDs, --extract FILE and --exclude FILE variants, --chr with --from-bp and --to-bp a region.

Linkage disequilibrium

plink2 --pfile chr21_qc --indep-pairwise 50 5 0.2 --out ld
cat ld.prune.in
plink2 --pfile chr21_qc --r2-unphased --ld-window-r2 0.2 --out ld
cat ld.vcor

Variants close to each other are inherited together, so their genotypes are correlated: linkage disequilibrium, measured as r2. --indep-pairwise 50 5 0.2 moves along the chromosome in windows of 50 variants, 5 at a time, and of every pair with r2 above 0.2 keeps one: ld.prune.in lists the variants kept (6 of the 9), ld.prune.out the others. Analyses that expect independent variants – principal components, relatedness – use the pruned set (--extract ld.prune.in). --r2-unphased lists the pairs: rs559962037 and rs556687069, 229 bases apart, have r2 = 0.96 – they are nearly always inherited together.

Association: does a variant go with a trait?

The 1000 Genomes data has no trait to study, so these examples use synthetic data made for PLINK's own tests: 603 invented people, 30 variants (v1 … v30) and three phenotypes – BINARY (case 2 or control 1) and QUANT (a number), both drawn at random, and FIRTH, which makes every carrier of v1's ALT allele a case – with two covariates, C1 and C2 (in a real study: age, sex, principal components).

D=/data/examples/plink2
head -3 $D/synthetic_phenotypes.tsv
plink2 --vcf $D/synthetic_glm.vcf --pheno $D/synthetic_phenotypes.tsv --covar $D/synthetic_covariates.tsv --glm hide-covar --out assoc
ls assoc.*
cut -f 3,9,11-16 assoc.QUANT.glm.linear | head -5

--glm tests every variant with every phenotype: linear regression for a quantitative trait (assoc.QUANT.glm.linear), logistic regression for cases and controls (.glm.logistic.hybrid), with the covariates in each model (hide-covar: their own lines are left out). A line gives the variant, the allele tested (A1) and its frequency, the number of people, the effect – BETA, the change of the trait for each copy of A1, or OR, the odds ratio – its standard error, the test statistic and the p-value. QUANT and BINARY are random, so their p-values are spread between 0 and 1: of 30 tests, one or two fall below 0.05 by chance (here one for QUANT, none for BINARY). That is why a study is judged against the number of its tests – 0.05/30 here, and 5×10−8 for the million tests of a genome-wide study.

sort -g -k16,16 assoc.FIRTH.glm.logistic.hybrid | cut -f 3,10,13,16,17 | head -4

For FIRTH, v1 stands out. Every carrier of its ALT allele is a case – complete separation, for which ordinary logistic regression finds no odds ratio: it grows without end. PLINK then uses Firth's regression (FIRTH? Y), and still marks the result UNFINISHED: the odds ratio is in effect infinite. ERRCODE says when a result is not to be trusted as it stands. No other variant passes 0.05/30 = 0.0017. The p-values as a picture, in Python (a small "Manhattan plot"):

Peaks: ChIP-seq and ATAC-seq (MACS3)

In ChIP-seq, the DNA that a protein holds – a transcription factor, a modified histone – is pulled out of the cell with an antibody against the protein and sequenced, so its reads pile up where the protein sits on the genome. MACS3 finds those piles, the peaks: places with more reads than chance – and the control experiment – would put there. Its command hmmratac does the same for ATAC-seq, whose reads mark the open chromatin.

The examples work in a folder of your own:

The reads

/data/examples/chipseq/ holds MACS's own test data: the reads of a ChIP-seq of CTCF – a protein that binds one DNA motif at tens of thousands of places in the genome and folds the chromatin into loops – and of its control, the same chromatin sequenced without the antibody (the "input"). There are about 50,000 of each, all on human chromosome 22, at their positions on hg19 (GRCh37).

zcat /data/examples/chipseq/CTCF_SE_ChIP_chr22_50k.bed.gz | head -3
zcat /data/examples/chipseq/CTCF_SE_ChIP_chr22_50k.bed.gz | wc -l
zcat /data/examples/chipseq/CTCF_SE_CTRL_chr22_50k.bed.gz | wc -l

Each line is a read where it mapped: chromosome, start and end (BED counts from 0) and its strand. The reads are 101 bases long, but the DNA fragments they were read from are longer: a read is one end of its fragment, on the strand it was read from. MACS3 reads BAM files as well (-f BAM) – sorted or not, it needs no index – and the pairs of a paired-end run (-f BAMPE, -f BEDPE; see below).

Calling the peaks

macs3 callpeak -t /data/examples/chipseq/CTCF_SE_ChIP_chr22_50k.bed.gz -c /data/examples/chipseq/CTCF_SE_CTRL_chr22_50k.bed.gz \
    -f BED -g 52000000 -n ctcf -B --outdir ctcf

-t is the ChIP (the "treatment"), -c the control, -f the format of both. -g is the effective genome size, the part of the genome that reads can map to: hs for human, mm for mouse, ce and dm for worm and fly, or a number – here the reads come from chromosome 22 alone, about 51 million bases, and MACS's own tests give 52,000,000. -n names the files, --outdir is their folder, and -B writes the pile-ups as bedGraph files as well. MACS3 is a Python program: each command starts the Python that comes with it, with NumPy, SciPy and the rest, which takes a few seconds – the first time a little longer, as about 45 MB are loaded.

Its messages say what it does, step by step ([RSS unavailable]: in the browser it cannot measure the memory it uses).

  • #1 it reads the tags – the reads – and keeps at most one at the same position on the same strand (--keep-dup 1): more are taken for copies made by PCR. 49,622 ChIP reads become 48,047.
  • #2 it builds its model: around a binding site, the reads of the + strand pile up on its left and those of the − strand on its right, half a fragment away on each side. From 469 pairs of such piles MACS works out the fragment length d: 228 bases. Each read is then extended to d bases, in its direction, and the fragments are piled up.
  • #3 it calls the peaks: at each position the ChIP's pile-up is compared with the number of fragments expected there, the local λ – the most of the control's pile-up over d, 1,000 and 10,000 bases around, and of the genome's average, scaled to the same number of reads – with a Poisson test. Its p-values become q-values (Benjamini–Hochberg), and the regions with q below 0.05 (-q 0.05) are the peaks. The control is what makes the test fair: regions that every sample has more reads in – open chromatin, repeats, copies of the genome – have more control reads too.

The peaks

ls ctcf
head -3 ctcf/ctcf_peaks.narrowPeak
wc -l ctcf/ctcf_peaks.narrowPeak
sort -k9,9gr ctcf/ctcf_peaks.narrowPeak | head -3

730 peaks. A line of ctcf_peaks.narrowPeak (ENCODE's narrowPeak format: BED with four more columns) is a peak: chromosome, start, end, name; a score (−10·log10q, as a whole number of at most 1000); the strand (none: .); the fold enrichment at the summit – the pile-up over the local λ –, −log10p and −log10q; and where the summit, the highest point of the pile-up, lies, counted from the start. The strongest peak (the last command sorts by the q-value) has 58 times as many fragments at its summit as expected, and a q-value of 10−188. The other files: ctcf_peaks.xls, the same peaks as a table for a spreadsheet, with the command and the settings at the top (a text file, despite its name; open it in the Files tab); ctcf_summits.bed, the summit of each peak; ctcf_treat_pileup.bdg and ctcf_control_lambda.bdg (with -B), the pile-up of the ChIP and the local λ along the chromosome; and ctcf_model.r, an R script that draws the model.

These are MACS's own results: its test of the same command keeps the peaks it expects in run_callpeak_narrow0_peaks.narrowPeak. Apart from the names, which come from -n, the two files are the same, byte for byte:

On the genome

The fold enrichment along the chromosome is the ChIP's pile-up divided by the local λ: macs3 bdgcmp works it out from the two bedGraph files. Then the peaks and the enrichment go to the Genome browser, on hg19 with its genes (a genome hosted by the IGV team: it needs the internet).

macs3 bdgcmp -t ctcf/ctcf_treat_pileup.bdg -c ctcf/ctcf_control_lambda.bdg -m FE -o ctcf/ctcf_FE.bdg
igv --genome hg19 ctcf/ctcf_peaks.narrowPeak ctcf/ctcf_FE.bdg --locus chr22:39,700,000-39,800,000

Nine peaks in these 100,000 bases. -m chooses what bdgcmp computes: FE, logFE, logLR, ppois (−log10 of the Poisson p-value at each position), qpois, subtract …; macs3 bdgpeakcall calls peaks from such a track with a cutoff of your own.

The model is drawn by R: the script writes ctcf_model.pdf in the folder it runs in.

cd ctcf && Rscript ctcf_model.r && cd ..
open ctcf/ctcf_model.pdf

Its first page shows the two piles of tags, the + strand (red) left and the − strand (blue) right of the binding sites; its second the correlation of the two strands for each shift between them, highest at 228.

Paired-end reads

ATAC-seq: open chromatin, with hmmratac

In ATAC-seq the enzyme Tn5 cuts the DNA where it is not wrapped around nucleosomes and adds the adapters of the sequencer there; the fragments between two cuts are read from both ends. A fragment shorter than about 150 bases comes from open DNA; longer ones span one, two or three nucleosomes. /data/examples/atacseq/ has the 5,771 fragments that fall on chromosome I of baker's yeast (230,218 bases), of MACS's own test of HMMRATAC – a yeast ATAC-seq (SRA run SRR1822137).

zcat /data/examples/atacseq/yeast_SRR1822137_chrI.bedpe.gz | awk '{ n[$3 - $2 < 150 ? "shorter than 150" : "150 or longer"]++ } END { for (k in n) print k, n[k] }'
macs3 hmmratac -i /data/examples/atacseq/yeast_SRR1822137_chrI.bedpe.gz -f BEDPE --randomSeed 12345 -n atac --outdir atac
head -3 atac/atac_accessible_regions.narrowPeak
wc -l atac/atac_accessible_regions.narrowPeak

HMMRATAC learns the lengths of four kinds of fragment – free of nucleosomes, and spanning one, two or three – from the data (its messages: means of 50, 174, 357 and 549 bases); it splits the signal into those four, trains a hidden Markov model with three states – open, nucleosome, background – on regions with strong signal, and decodes the chromosome with it. The accessible regions are the open stretches and their flanking nucleosomes: 56 here (atac_accessible_regions.narrowPeak, with the summit). atac_model.json is the model, which --model uses again on other data. It picks fragments at random to learn their lengths: --randomSeed makes a run repeatable. With so few fragments the model depends on that draw – try another seed – while a real experiment has millions. The positions are those of the yeast genome sacCer3:

igv --genome sacCer3 atac/atac_accessible_regions.narrowPeak --locus chrI:120,000-150,000

More

macs3 has fourteen commands; macs3 COMMAND -h lists the options of each. Besides callpeak, hmmratac and bdgcmp: callpeak --broad joins nearby peaks into broad regions, for histone marks such as H3K27me3 (NAME_peaks.broadPeak and .gappedPeak); bdgpeakcall and bdgbroadcall call peaks from a bedGraph track; bdgdiff finds the differences between two conditions; cmbreps combines replicates; bdgopt changes a track; filterdup removes duplicate reads; predictd works out only the fragment length; pileup piles up the reads; randsample takes a sample of them; refinepeak refines the summits; callvar calls variants in the peaks – from reads of a ChIP and its control. In the Galaxy tab, the tool MACS3 callpeak (section Peak calling) runs macs3 callpeak on BAM or BED datasets.

MACS3 3.0.5 is compiled to WebAssembly from its released source – its C and Cython parts, with those of hmmlearn – by the genomics-wasm project, and gives the same peaks, tracks and tables as MACS3 on Linux, byte for byte – its models the same but for the last decimals (see Programs and versions). It runs as one process: callvar -m N works through its N parts one after another, with the same result. It keeps all the reads in memory: a chromosome, or the genome of yeast, is fine; the tens of millions of reads of a whole human genome need more memory than a browser tab has (see Limits).

The files

Alignments and trees

Pairwise alignment (needleman_wunsch, smith_waterman), multiple alignment (kalign, muscle), trees (FastTree), and long DNA alignments (lastz).

The examples work in a folder of your own:

Two sequences

needleman_wunsch --printscores GATTACA GCATGCT
smith_waterman --printseq ACACACTA AGCACACA

needleman_wunsch aligns two sequences from end to end (global); smith_waterman finds the best-matching parts (local) and lists every good hit. The scores they use unless told otherwise differ: needleman_wunsch --match 1 --mismatch -2 --gapopen -4 --gapextend -1, smith_waterman --match 2 --mismatch -2 --gapopen -2 --gapextend -1. For proteins --scoring BLOSUM62 (also PAM30, PAM70, BLOSUM80). With --file pairs.fasta they align the sequences of a file two at a time.

needleman_wunsch --scoring BLOSUM62 --gapopen -10 --gapextend -1 --printscores \
  MVLSPADKTNVKAAWGKVGAHAGEYGAEALERMFLSFPTTKTYFPHF MVHLTPEEKSAVTALWGKVNVDEVGGEALGRLLVVYPWTQRFFESF

lcs SEQUENCE (also from seq-align) lists the substrings that occur twice in a sequence, longest first.

Multiple alignment

kalign -i /data/examples/sequences/myoglobins.fasta -o myoglobins.afa
muscle -in /data/examples/sequences/myoglobins.fasta -out myoglobins_muscle.afa

A tree

FastTree builds an approximately-maximum-likelihood tree (JTT+CAT for proteins; -nt for DNA, with -gtr for the GTR model). The numbers before the branch lengths are local support values (0–1). The Files tab draws a .nwk file as a tree; in R, ape::read.tree() reads it, in Python Bio.Phylo.

Long DNA: lastz

lastz aligns long DNA sequences – a region against a chromosome, two related genomes. [multiple] after the target file means it has more than one sequence; quote it, because [ ] mean something to the shell.

Most bioinformatics files are text. The GNU tools – grep, sed, awk, sort, cut, uniq, wc – answer many questions in one line, without a program of their own.

Look and count

head -3 /data/examples/tables/yeast_genes.csv | cut -c 1-120

Columns: cut, sort, uniq

# essential genes (column 3 of the yeast table: 1 = essential)
cut -d, -f3 /data/examples/tables/yeast_genes.csv | tail -n +2 | sort | uniq -c
# the variant positions of a VCF, as a list
bcftools view -H /data/examples/variants/NA12878.calls.vcf.gz | cut -f 1,2 | head -5

Careful with cut -d, on CSV files: a field with a comma inside quotes is cut there too. In the yeast table the location ("Golgi, vesicles & vacuole") and the description have such commas, so every column after the location – the chromosome is column 16 – would be counted wrong. gawk can read the quoted fields (FPAT describes what a field looks like); pandas and R read CSV files properly too:

awk -v FPAT='[^,]*|"[^"]*"' 'NR > 1 { print $16 }' /data/examples/tables/yeast_genes.csv | sort | uniq -c | sort -rn | head -5

grep -v "^#" /data/examples/annotation/cyp2c_slices.gff3 | cut -f 3 | sort | uniq -c

Scripts and pipelines

Commands that work once belong in a script – so that they run again tomorrow, on new data, and show exactly what was done.

The examples work in a folder of your own:

A bash script

Write the commands into a file – in the Files tab, or with a here-document as below – and run it with bash:

cat > count_reads.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail          # stop at the first error
for f in "$@"; do
  n=$(( $(wc -l < "$f") / 4 ))
  echo -e "$(basename "$f")\t$n"
done
EOF
bash count_reads.sh /data/examples/reads/*.fastq

"$@" are the file names given to the script; set -euo pipefail makes it stop at the first command that fails, instead of carrying on with half a result. After chmod +x count_reads.sh it also starts as ./count_reads.sh.

A whole analysis in one script

cat > call_variants.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail
ref=/data/examples/reads/reference.fa
r1=/data/examples/reads/NA12878_R1.fastq
r2=/data/examples/reads/NA12878_R2.fastq
fastp -i "$r1" -I "$r2" -o trimmed_1.fastq -O trimmed_2.fastq -h fastp.html -j fastp.json 2> fastp.log
minimap2 -ax sr -R '@RG\tID:NA12878\tSM:NA12878' "$ref" trimmed_1.fastq trimmed_2.fastq 2> minimap2.log | samtools sort -o mapped.bam -
samtools index mapped.bam
bcftools mpileup -f "$ref" mapped.bam 2> /dev/null | bcftools call -mv -Oz -o calls.vcf.gz
bcftools filter -i 'QUAL>=20 && INFO/DP>=5' -Oz -o filtered.vcf.gz calls.vcf.gz
echo "variants: $(bcftools view -H filtered.vcf.gz | wc -l)"
EOF
bash call_variants.sh

Asking from code

Each card uses a REST API: a web address goes in, data comes out – JSON for most, FASTA or text for sequences. The same works in a notebook:

import requests

r = requests.get("https://rest.ensembl.org/lookup/symbol/homo_sapiens/CYP2C19",
                 headers={"Content-Type": "application/json"})
r.raise_for_status()          # stop here if the service said no
gene = r.json()
gene["id"], gene["seq_region_name"], gene["start"], gene["end"]
library(jsonlite)
gene <- fromJSON("https://rest.ensembl.org/lookup/symbol/homo_sapiens/CYP2C19?content-type=application/json")
c(gene$id, gene$seq_region_name, gene$start, gene$end)

In the browser, R can only make GET requests (a URL); for services that need a POST request – BLAST, VEP with positions, the PDB search – use Python. More in the recipe Databases from code.

Good practice

  • Databases change. New releases add, correct and remove entries; a query can give another answer next month. Note the date – the notebook of your queries does – and, for positions on a genome, the assembly: GRCh38 (hg38) and GRCh37 (hg19) number the same base differently.
  • Annotations are predictions. VEP calls rs4244285 synonymous – yet it is CYP2C19*2, a loss-of-function allele that changes the splicing of the gene (see Genes, genomes and variants). Look at the clinical significance and the literature before you conclude.
  • The services are shared by scientists everywhere. Ask for what you need, not thousands of queries in a quick loop: Ensembl allows about 15 requests a second, NCBI 3. A request that gets no answer at all is sent again (twice) by the tab; for code, see the recipe.
  • When a query fails, the message says why: Not found (404) – check the identifier; did not accept the query (400) – check what you typed; slow down (429) – wait a minute; not answering (5xx) or no answer that the page could read – the service is busy or down: try again later.
Public services

Only what you type into a form is sent to the service (for BLAST, also your e-mail address). These are public services that keep logs: never type or paste personal or patient data into them.

UniProt

UniProtKB, the UniProt Knowledgebase, is the reference collection of protein sequences and of what is known about each protein. The UniProt card shows its entries laid out like the pages of uniprot.org, from live data.

Reviewed and unreviewed

UniProtKB has two parts. Swiss-Prot (★ Reviewed) entries are read and written by expert curators, from the literature; there are about 575,000 of them. TrEMBL (Unreviewed) entries – about 150 million – are annotated automatically, mostly from genome sequences (numbers of release 2026_03). When a reviewed entry exists, use it.

Each entry has an accession (P04637), which never changes and is the one to cite, and an entry name (P53_HUMAN). Its annotation score (1 to 5) says how much is known about it, not how correct it is.

Protein Data Bank

The Protein Data Bank (PDB) holds the 3D structures of proteins, DNA, RNA and their complexes that have been determined by experiment – over 260,000 of them. Each has a four-character PDB ID, such as 1MBN. The card searches the RCSB PDB, shows an entry, and loads it into the 3D viewer.

Search

Type a PDB ID, a protein name, a UniProt accession or any words. Auto decides which it is; the menu next to it can say so instead (Protein name, UniProt accession, Full text). Narrow the results with Human only, Contains DNA and the method (X-ray, cryo-EM, NMR); sort by Best match, Newest first or Best resolution. The results come ten to a page, each with Load in 3D and Details.

An entry

  • Method and resolution. X-ray crystallography and cryo-EM give a resolution in ångström (Å): the smaller the number, the finer the detail. Roughly: at 1.2–1.5 Å and better single atoms can be told apart; around 2 Å the side chains are clear; beyond about 3.5 Å the path of the chain shows, and the side chains are largely modelled. NMR structures have no resolution; they are a set of models.
  • The paper that describes the structure.
  • Macromolecules: each kind of molecule, its chains (A, B …), type, length, organism, and the UniProt entry of the protein – click it to open it in the UniProt card.
  • Small molecules: ligands, ions and sugars, each with its three-letter code (HEM is haem, HOH water) and a drawing.
  • Biological assemblies: the file holds the asymmetric unit – the chains the experiment saw together – which is not always the molecule as it exists in the cell. The assembly says which it is (a monomer, a dimer …).
  • Files: Look inside the .pdb file shows its records with the columns coloured; Save .pdb to my files or Save .cif keeps the file in ~/structures; Send to notebook adds Python or R code that fetches the entry and its file.

The file

A structure is a text file with one line per atom. In the old .pdb format the columns are fixed:

ATOM      1  N   VAL A   1      -2.900  17.600  15.500  1.00  0.00           N
ATOM      2  CA  VAL A   1      -3.600  16.400  15.300  1.00  0.00           C

After ATOM and the atom's number come the atom name (CA is the alpha carbon), the residue (VAL), the chain (A), the residue number, the x, y and z coordinates in ångström, the occupancy and the B-factor (0 in this old file), and the element.

ATOM lines are the protein or nucleic acid, HETATM lines the ligands and water. The B-factor says how much an atom moves or how uncertain its position is (in AlphaFold models this column holds the pLDDT confidence instead). Very large structures exist only in the newer .cif (mmCIF) format. Both are read by the 3D viewer and by Biopython (Bio.PDB) in a Python notebook.

AlphaFold DB and InterPro

Two cards for what a protein's sequence says about it: AlphaFold DB has a predicted 3D structure for almost every protein in UniProt; InterPro finds its families, domains and important sites.

AlphaFold DB

AlphaFold predicts a protein's structure from its sequence. AlphaFold DB (EMBL-EBI and Google DeepMind) holds the predictions for over 200 million UniProt proteins. Type a UniProt accession and Search:

  • The table names the model (AF-P69905-F1), the protein and its organism, and the mean pLDDT.
  • The picture is the predicted aligned error (PAE).
  • Show in the 3D viewer loads the model, coloured by confidence; Save the model (.pdb) to my files keeps it in ~/structures.

How far to trust a model

pLDDTColourMeaning
above 90dark bluevery high confidence: side chains placed well too
70 – 90light blueconfident: the backbone is right
50 – 70yellowlow confidence
below 50orangevery low: often a region with no fixed structure (disordered), not a real shape

pLDDT is a confidence for each residue, about its own surroundings. It says nothing about how the domains lie relative to each other: that is what the PAE plot shows. Its colour in column x (the scored residue, along the top) and row y (the aligned residue, down the side) is the error AlphaFold expects in the position of residue x when the model is lined up on residue y: dark is a small error. Dark squares along the diagonal are domains placed confidently; light areas between them mean their arrangement is uncertain.

In the 3D viewer the model's panel has the pLDDT profile (click it to go to a residue), the PAE plot (drag a box over it: the two stretches of residues are selected, with the mean expected error between them), Hide pLDDT < 50, and Superpose onto… an experimental structure. A model is a prediction: where an experimental structure exists, compare them.

Genes, genomes and variants

Four cards for genes, genomes and sequencing data: Ensembl, NCBI, the UCSC Genome Browser and the European Nucleotide Archive.

Ensembl

Ensembl (EMBL-EBI) annotates the genomes of vertebrates and model organisms: genes, transcripts, proteins, variants, and how genes of different species are related. The card asks its REST API, which serves the latest release – for human, on the GRCh38 assembly.

Gene
A species and a gene symbol (CYP2C19) or Ensembl gene ID (ENSG…). The answer gives the gene's ID, type (biotype), position and strand, and a table of its transcripts – which is the canonical one, how many exons, how long the protein is – with buttons that save each transcript's cDNA, CDS or protein sequence. Save the gene sequence (FASTA); for human genes, Show in the Genome browser (GRCh38).
Sequence
The sequence of an Ensembl gene, transcript or protein ID. genomic: the whole region, introns included (with extra bases on each side if you ask); cDNA: the exons of a transcript, untranslated regions included; CDS: from the start codon to the stop codon; protein.
Variant effect (VEP)
The Variant Effect Predictor: an rs ID (rs4244285), an HGVS description (ENST00000646891.2:c.1799T>A), or a chromosome, position, reference and alternative base on GRCh38 (10 94781859 G A). The answer gives the most severe consequence; the known variants at that position, with their clinical significance; allele frequencies (1000 Genomes, gnomAD); and for each transcript the consequence, its impact (HIGH, MODERATE, LOW, MODIFIER), the amino-acid change and the SIFT and PolyPhen predictions. A consequence is worked out from the position and the transcripts alone: rs4244285 comes out as synonymous (Pro227Pro), yet it is CYP2C19*2, the commonest loss-of-function allele of the gene – the base change makes a new splice site, and the mRNA is spliced wrongly. Read the clinical significance and the papers too.
Orthologues
The genes in another species – or in all of them – that descend from one gene of their last common ancestor: orthologues are separated by a speciation event (paralogues by a duplication within a genome).
Genes in a region
Every gene between two positions of a chromosome (at most 5 Mb).
GRCh38 and GRCh37

The same base has different positions on the two human assemblies: rs4244285 is at chr10:94,781,859 on GRCh38 and chr10:96,541,616 on GRCh37 (hg19). The example data of the workbench, and many older papers, use GRCh37. In code, Ensembl's GRCh37 server is https://grch37.rest.ensembl.org; the UCSC card has both.

The DNA of any region of a genome assembly: human hg38 (GRCh38) and hg19 (GRCh37), mouse, zebrafish, fly, worm and yeast. European Nucleotide Archive

ENA (EMBL-EBI) – with its partners NCBI's SRA and DDBJ – keeps the raw data of published sequencing experiments. Sequencing runs takes a study (PRJEB37886), sample or run (SRR098401) accession, or a query in ENA's language (tax_eq(9606) AND library_strategy="AMPLICON"), and lists the runs: organism, instrument, library strategy and layout, number of reads, and the FASTQ files. Mind the size

A human genome or exome run is many gigabytes (the two FASTQ files of SRR098401 are 7.5 and 7.7 GB): far more than fits in a browser. Small runs – of viruses, bacteria, amplicons – are a few megabytes to a few hundred. The recipe Databases from code shows how to take just the first reads of a large file.

Sequence by accession gives any ENA/GenBank sequence as FASTA (MN908947.3 is the first SARS-CoV-2 genome).

BLAST

BLAST finds the sequences in a database that are similar to yours – the first thing to do with an unknown sequence. The BLAST card sends the search to EMBL-EBI, where it runs for seconds to a few minutes, and shows the hits.

  1. Program – which depends on what your sequence is and what you search:
    ProgramYour sequenceSearches
    blastpproteinproteins
    blastnDNADNA
    blastxDNA, translated in all six reading framesproteins

    Protein searches find relatives much further back in evolution than DNA searches: when the sequence codes for a protein, compare proteins (blastp, or blastx from DNA).

Interactions and networks

Which proteins work together? STRING collects known and predicted associations between proteins and tests lists of genes for shared functions; IntAct holds the interactions that experiments have shown, curated from papers; NDEx shares whole networks – pathways, interactomes, the networks of published papers. Each answer can be opened in the Networks tab, to style with your own data and analyse.

STRING

STRING scores how likely two proteins are to work together, from seven kinds of evidence (channels): experiments, curated databases, genes switched on together (co-expression), genes that sit together in genomes, are fused, or are found in the same species, and papers that mention them together (text mining). The combined score, from 0 to 1, puts them together.

Interaction network: type gene or protein names (or UniProt or Ensembl IDs), one per line, choose the species, and Search.

  • Minimum confidence: high (0.7) keeps the associations STRING is most sure of; medium (0.4) is STRING's default.
  • Add neighbours: adds the proteins most strongly connected to yours, to show the neighbourhood.
  • The picture is STRING's own drawing; the table has a row for each pair, with the combined score and the scores of its main channels. Open in Networks makes the same network in the Networks tab, with the edges as wide as their scores.

An association is not always a physical contact: two enzymes of one pathway are associated without ever touching. Look at where a score comes from before you call it an interaction – or, in the Networks tab's From STRING…, ask for physical interactions only.

Functional enrichment: type a list of genes – those an experiment changed, say. STRING says which GO terms, pathways (KEGG, Reactome, WikiPathways) and other annotations are more common among them than among all the genes of the species, with false discovery rates (FDR). Show keeps one category. Their network in Networks opens the network of the list.

IntAct

IntAct is a database of molecular interactions, curated by hand from published experiments: which molecules bind, how that was shown (yeast two-hybrid, co-immunoprecipitation, a crystal structure …), and in which paper. Type a UniProt accession (P04637) or a protein name; several, separated by spaces, find the interactions of each.

  • IntAct stores each experiment as a separate piece of evidence; the table joins them, one row for each pair of molecules, with the number of pieces of evidence, the methods and the PubMed IDs of the papers.
  • The MI score (0 to 1) is IntAct's confidence in an interaction: higher when more experiments, of more kinds and from more papers, show it. Above 0.6 is usually called high confidence, above 0.45 medium.
  • Open in Networks: the network of the molecules you asked for and their partners, with an edge for each pair, as wide as its MI score. Isoforms of a protein (P04637-2) are counted as the protein itself.

NDEx

The Network Data Exchange is a public library of networks: curated pathways (NCI-PID, SIGNOR, WikiPathways), interactomes, and networks that authors share with their papers. Search it by words – a pathway, a gene, a disease, an author. The table lists each network's size and its Rights: each network has its own licence, so read it before you reuse one. Open in Networks opens a network (of up to 50,000 edges) with its layout, and all the columns of its nodes and edges.

Pathways, GO and enrichment

What does a protein do? Reactome names the pathways it takes part in, the Gene Ontology card lists the standard terms for its function, the processes it is part of and where it is in the cell, and g:Profiler finds what a whole list of genes has in common. Which proteins it works with – STRING, IntAct and NDEx – is on the page Interactions and networks.

Reactome

Reactome is a curated database of human biological pathways – reactions, the molecules in them, and how they connect – with predictions for other species. Type a UniProt accession: the answer lists the pathways the protein is in, with Diagram for those that have one; Disease marks pathways of a disease.

Gene Ontology

The Gene Ontology (GO) is a dictionary of terms that describe what genes do, so that all databases say it the same way. It has three parts (aspects):

AspectDescribesExample
Molecular functionwhat the protein does itselfGO:0003700 DNA-binding transcription factor activity
Biological processthe larger process it takes part inGO:0006915 apoptotic process
Cellular componentwhere in the cell it isGO:0005634 nucleus

GO terms of a protein (from QuickGO): type a UniProt accession, and choose an aspect or all three. Each term has an evidence code that says how it was assigned: EXP, IDA, IMP, IPI … from experiments; IBA, ISS from related genes; IEA automatically, without a curator; TAS, NAS from statements in papers. The qualifier says how the protein relates to the term (enables, involved in, located in, part of, or NOT).

Look up a term (from the Ontology Lookup Service) searches the terms of GO and other ontologies: the Human Phenotype Ontology (symptoms and signs), Mondo (diseases), Uberon (anatomy), the Cell Ontology, ChEBI (chemicals), the Sequence Ontology (the names of variant consequences used by VEP).

g:Profiler

Lists of genes – the genes changed in an experiment – are compared against GO and the pathway databases with an enrichment (over-representation) analysis: which terms occur more often in the list than among all the genes of the species? g:Profiler's g:GOSt answers for GO, KEGG, Reactome and WikiPathways at once. Type the genes (names or Ensembl IDs), choose the organism and the sources, and Search.

  • The p-values are adjusted for testing thousands of terms with g:Profiler's own method, g:SCS, made for the way GO terms overlap; terms below 0.05 are listed.
  • Genes is the number of your genes with the term, over the number of genes in the genome with it: a term with 3 of your genes out of 20 in the genome says more than 3 out of 2,000.
  • g:Profiler says which of your names it did not know – check their spelling, or use Ensembl IDs.

The test compares your list with the whole genome. If your genes could only come from a smaller set – the genes detected in your experiment – the whole genome makes many terms look enriched; on g:Profiler's own site you can give that set as the background. STRING's enrichment (on Interactions and networks) and the Networks tab's Analyse → Functional enrichment do the same test, and can use the nodes of a network as the background.

In a notebook, the recipe Databases from code asks UniProt about many proteins at once and reads the answer as a table: add go_p, go_f or go_c (biological process, molecular function, cellular component) to the fields of its query, and the table has their GO terms.

The genome browser

The genome browser (igv.js, the web edition of IGV) draws data along a genome: mapped reads, variants, genes, coverage. It is where you check, with your own eyes, what a program has claimed – a variant call, a deletion, a badly mapped region.

The genome

Choose it at the top left:

  • Example: CYP2C19 / CYP2C9 slices – the reference of the example reads: two pieces of human chromosome 10 (GRCh37), called human_CYP2C19 and human_CYP2C9, with their genes. Use it for anything made from the example data.

Reading the reads

  • The coverage track on top shows how many reads cover each base. Where many reads disagree with the reference, the bar is coloured by the bases they have.
  • Each bar is a read, coloured by its strand: pink forward, blue reverse. A coloured letter in a read is a base that differs from the reference; faint letters are bases of low quality.
  • A purple I is an insertion, a black line a deletion. Faint reads have mapping quality 0 (MAPQ 0): they fit equally well somewhere else in the genome.
  • A real heterozygous SNV shows the other base in about half the reads, on both strands; a sequencing error shows up in one or two reads, or on one strand only.

Network analysis

The Analyse menu of the Networks tab measures the network and its nodes, ranks its hubs, divides it into clusters and asks what its genes have in common. Before you start

  • Every analysis treats the network as undirected: an edge A → B joins A and B. Several edges between the same two nodes count as one, and self-loops are left out (the statistics count them).

MCODE

MCODE (Bader & Hogue 2003) first scores every node: it finds the most densely connected core of the node's neighbourhood (the highest k-core) and multiplies its density by k. It then grows a cluster from the best-scoring node, taking in the neighbours whose scores are within 20% of the seed's (Node score cutoff 0.2), and so on outwards; then from the best node not yet in a cluster, and so on. A cluster is kept when it has a 2-core (k-core); the haircut removes nodes joined to it by a single edge; fluff (off) would add dense neighbours. The score of a cluster is its density times its number of nodes. The settings are those of the Cytoscape app clusterMaker2, whose implementation the tab follows step by step.

MCL

The Markov cluster algorithm (van Dongen; Enright et al. 2002) follows random walks on the network: they stay longer within groups that are well joined. In rounds, it spreads the walks one step further (expansion) and strengthens the strong paths and weakens the weak ones (inflation: each value to the power r, here 2), until nothing changes; each group of nodes that the walks no longer leave is a cluster. Larger inflation, more and smaller clusters (1.4 to 6 are usual). With Edge weights – STRING's score, say – strong edges hold clusters together. It runs as the Python package markov_clustering runs it, with a self-loop on each node as strong as its strongest edge (as Cytoscape's clusterMaker2 adds them); values below 0.001 are dropped, and it stops after 100 rounds (the panel says if it stopped before it converged).

Louvain

The Louvain method (Blondel et al. 2008) looks for the division with the highest modularity: the share of edges inside groups, minus the share expected if the same nodes, with the same numbers of edges, were joined at random (Newman 2006). It moves single nodes to the neighbouring group that raises it most, then treats each group as one node and starts again, until it stops rising. A modularity above about 0.3 means a clear division. Resolution above 1 gives more, smaller communities; below 1, fewer and larger. It runs as networkx's louvain_communities does, but takes the nodes in the order of the table instead of shuffling them: the same network always gives the same communities here (networkx's can differ a little from run to run).

Functional enrichment

Analyse → Functional enrichment asks which GO terms (processes, functions, cellular components), pathways (KEGG, Reactome, WikiPathways) and other annotations are more common among a set of genes than among all the genes of the species – an over-representation test, corrected for testing thousands of terms. The genes can be all the nodes, the selected ones, or a cluster (the enrichment link of each cluster).

  • STRING adds its own annotations (publications, tissues, protein domains, STRING's clusters), reports false discovery rates (Benjamini–Hochberg), and can use the nodes of the network as the background – tick Background when the network is a selection (say, the genes detected in your experiment) rather than a random set.
  • g:Profiler reports p-values adjusted with its own method, g:SCS, made for the way GO terms overlap.

Click a term to select its genes on the network; Save the table writes the terms as CSV. Two cautions: genes that are connected in STRING tend to share annotations, because shared annotations are part of what connects them; and an enriched term says the genes are annotated with it more often than by chance, not that the term explains your experiment.

How the analyses were checked

The analyses were written for the workbench (file assets/js/net-algo.js) and compared with independent programs on five networks – the karate club, the characters of Les Misérables, the Florentine families, a random network and the STRING network of the recipe – 215 comparisons, all equal:

  • networkx 3.4.2: degrees, distances, closeness, betweenness and edge betweenness, clustering coefficients, eccentricity, neighbour degrees, components, core numbers, maximal cliques and modularity;
  • markov_clustering (Python): MCL, with and without weights;
  • line-by-line Python versions of clusterMaker2's MCODE and of networkx's Louvain (without the shuffle), and of the definitions in the cytoHubba paper for its other methods.

Where the published definitions leave a choice, the tab makes these:

  • Betweenness and stress count each pair of nodes once (not once from each end); NetworkAnalyzer's BetweennessCentrality is divided by (N − 1)(N − 2)/2, for N the nodes of the node's component.
  • EPC draws its 1,000 random networks from a fixed seed, so that the same network always gives the same scores.
  • BottleNeck takes the tree of a breadth-first search from each node, each node under the node that reached it first, and counts a node (itself included) under the nodes above it.
  • Radiality (cytoHubba): the sum of (Δ + 1 − distance) to the other nodes of the component, divided by their number, as radiality was first defined (Valente & Foreman 1998), times the component's share of all the nodes.

import time
import requests

def post_json(url, data, tries=4):
    """POST data as JSON; when the service is busy or does not answer, wait and try again."""
    for attempt in range(tries):
        try:
            r = requests.post(url, json=data, headers={"Content-Type": "application/json", "Accept": "application/json"})
            if r.status_code not in (429, 500, 502, 503, 504):
                r.raise_for_status()
                return r.json()
        except requests.exceptions.ConnectionError:
            pass
        time.sleep(2 ** attempt)
    raise RuntimeError(f"no answer from {url} – try again in a few minutes")

3. Reads across an intron

6. DESeq2

The design ~ cell + dex compares treated with untreated cells of the same cell line. Genes with almost no reads are left out first. The first library(DESeq2) downloads about 40 packages – give it a minute; DESeq() takes about as long.

library(DESeq2)
dds <- DESeqDataSetFromMatrix(countData = counts, colData = samples, design = ~ cell + dex)
dds <- dds[rowSums(counts(dds)) >= 10, ]
dds <- DESeq(dds)
res <- results(dds, contrast = c("dex", "trt", "untrt"), alpha = 0.05)
summary(res)

DESeq() normalises for the depth of each sample (size factors), estimates how much each gene varies between replicates (dispersion), and tests every gene. padj is the p-value adjusted for testing thousands of genes: a cut-off of 0.05 keeps the false discoveries near 5%.

9. The same with edgeR

fit <- glmQLFit(y, design)
qlf <- glmQLFTest(fit, coef = "dextrt")
summary(decideTests(qlf))

Expression data on an interaction network

The genes that a drug switches on or off make a list; the proteins they code for work together in a network. This recipe takes the result of the RNA-seq recipe – the genes that the steroid dexamethasone changes in airway smooth muscle cells – onto their STRING network, colours them by how much they changed, and looks for the hubs and clusters of the network and for what the clusters do. Most of it happens in the Networks tab, with the buttons below; the last steps do the same in Python.

1. The results of DESeq2

A row for each gene of the experiment: its Ensembl ID, its mean count (baseMean), how much it changed in treated cells (log2FoldChange: 1 is twice as much RNA, −1 half) and the adjusted p-value (padj). It is the file deseq2_dex_vs_untreated.csv that the RNA-seq recipe writes; a copy is in /data/examples/networks/airway_deseq2.csv.

2. From the table to a network

(if you made your own table in the RNA-seq recipe, choose it there instead). The tab finds the column of IDs and DESeq2's columns padj and log2FoldChange by their names. Keep the genes with padj < 0.01 and |log2FoldChange| ≥ 1.5 – 409 genes –, leave human, medium confidence (0.4) and all associations, and Make the network.

  • The IDs go to STRING, which finds the proteins – 357 of the 409 genes. Most of the others make no protein (long non-coding RNAs, pseudogenes), or have IDs that Ensembl has since retired: the airway data use an older annotation.
  • STRING returns the associations among the 357 proteins with a score of at least 0.4: 512 of them.
  • Every column of the table is added to the nodes – the rows are matched on the IDs that were sent, which the nodes keep in the column query.
  • The nodes are coloured by log2FoldChange – red up, blue down, grey unchanged – and sized by padj, the smallest p-values largest. The ends of the colour scale hold 95% of the genes, so that a few extreme ones do not wash out the rest (≤ and ≥ in the legend).

The finished network (the button at the top) was made in the same way on 13 October 2026, from STRING 12.5, and opens without the internet. STRING changes from version to version: made today, the network can differ a little.

5. Model and experiment, superposed

The Cα atoms of the model (residue n + 1) and of 1MBN (residue n) are laid on each other as closely as they go; the RMSD (root-mean-square deviation: the square root of the mean of the squared distances) then says how far apart they are.

from Bio.PDB import Superimposer

exp_ca, model_ca = [], []
af_chain = model[0]["A"]
for res in chain:
    n = res.id[1]
    if res.id[0] == " " and "CA" in res and (n + 1) in af_chain:
        exp_ca.append(res["CA"])
        model_ca.append(af_chain[n + 1]["CA"])
sup = Superimposer()
sup.set_atoms(exp_ca, model_ca)
print(f"RMSD over {len(exp_ca)} Cα atoms: {sup.rms:.2f} Å")

An RMSD around 1 Å means the prediction matches the experiment closely. To see it, run in the 3D viewer: load 1MBN; load af P02185; superpose AF-P02185-F1:A onto 1MBN:A (Viewer commands). The viewer reports a slightly smaller RMSD over a few residues fewer: it pairs the residues by aligning the sequences, leaves out pairs that end up more than 2 Å apart (loose ends) and fits again, as structure programs often do – the code above keeps every pair.

Databases from code

The Databases tab asks one question at a time. Code asks a hundred – and keeps the record. This recipe shows the patterns: a request and its answer as a table, many at once, a polite loop, what to do when a service is busy, NCBI with Biopython, and the first reads of a file too big to download.

1. A request that tries again

Web services are shared and sometimes busy: now and then they answer 429 (too many requests) or 5xx (a problem of the server), or nothing at all. A small function waits and asks again – and stops with a clear error for anything else (a wrong identifier gives 400 or 404).

import time
import requests
import pandas as pd

def ask(method, url, tries=4, **kwargs):
    """Make a request; when the service is busy or does not answer, wait and try again."""
    for attempt in range(1, tries + 1):
        try:
            r = requests.request(method, url, **kwargs)
            if r.status_code not in (429, 500, 502, 503, 504):
                r.raise_for_status()          # 400, 404 …: a mistake in the request – stop
                return r
            problem = f"HTTP {r.status_code}"
        except requests.exceptions.ConnectionError:
            problem = "no answer"
        if attempt == tries:
            raise RuntimeError(f"{problem} from {url} after {tries} tries – try again later")
        print(f"{problem} – trying again in {2 ** attempt} s")
        time.sleep(2 ** attempt)

def get_json(url, params=None):
    return ask("GET", url, params=params, headers={"Accept": "application/json"}).json()

gene = get_json("https://rest.ensembl.org/lookup/symbol/homo_sapiens/CYP2C19")
gene["id"], gene["seq_region_name"], gene["start"], gene["end"]

6. The first reads of a big file

A sequencing run is usually far too big for the browser – the reads of SRR098401 are 7.5 GB per file. A Range request downloads only the start of a compressed file, and zlib unpacks as much as arrived:

import zlib

url = "https://ftp.sra.ebi.ac.uk/vol1/fastq/SRR098/SRR098401/SRR098401_1.fastq.gz"
r = ask("GET", url, headers={"Range": "bytes=0-4999999"})      # the first 5 MB
text = zlib.decompressobj(16 + zlib.MAX_WBITS).decompress(r.content).decode()
lines = text.split("\n")
keep = (len(lines) - 1) // 4 * 4                                # whole reads only
with open("SRR098401_start_1.fastq", "w") as fh:
    fh.write("\n".join(lines[:keep]) + "\n")
print(keep // 4, "reads")
!head -n 8 SRR098401_start_1.fastq

The first reads of a run come from the edge of the flow cell, and are often poor (all N): for a fair sample, use reads from the middle of the file, or trim and filter first (Reads).

What is different in the browser

Everything in the workbench runs on your own computer, inside this web page: the programs are the real ones, compiled to WebAssembly, and Python and R are the real languages. That brings some limits a server would not have.

Speed and memory

  • Each program runs on one processor core; options for threads (-t, -p, -@, -j, --threads, --cpu) are ignored, with a note. Three programs are different: featureCounts counts on up to four threads (-T 1 to -T 4), Salmon runs its own helper threads, and PLINK 2 reads its files on threads of their own and computes on one or two (--threads 2 at most) – see programs on several threads. Programs run more slowly than on a server, and the speed depends on your computer: keep the data small.
  • A program, Python and R each have a few gigabytes of memory at most (WebAssembly is 32-bit: 4 GB is the ceiling, and browsers often allow less). Mapping reads to a whole human genome does not fit; regions, a few genes, bacterial and viral genomes do.
  • Python has no threads, no multiprocessing and no subprocess; input() does not work in a notebook. R cannot run system(): use a %%bash cell.

Programs on several threads

featureCounts, Salmon and PLINK 2 start threads that share the program's memory. A browser allows that only in a page that is cross-origin isolated: the page and its workers come with two headers, Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy, which also keep pictures of other sites out unless those sites allow them. Static hosting (GitHub Pages) cannot send the headers, so the workbench adds them itself with a small service worker (isolation-sw.js; it stores nothing): the first time you open the workbench, the page loads once more, at once. serve.py sends the headers itself.

  • If featureCounts, Salmon or PLINK 2 say that the page is not isolated, reload the page. It cannot be isolated when it was not opened over https (or from localhost), or when the browser does not allow service workers there – some private windows do not.
  • The other programs, Python and R do not need isolation, and work either way.
  • To turn isolation off – if a picture of another site does not show, say – open the workbench with ?isolation=off at the end of its address; open it without that to turn it on again.

Programs that are partly here

  • Cutadapt is a Python program: each command starts a Python of its own (Pyodide 314.0.7, CPython 3.14.2), which takes a few seconds, and the first one loads about 13 MB. It trims on one core.
  • LoFreq: lofreq call-parallel and lofreq vcfplot are not here – use lofreq call. lofreq somatic runs its steps one after another.
  • Kraken2 works with small databases: the database must fit in the browser's memory – a few hundred megabytes at most. The databases used for real samples (Kraken2's standard database is tens of gigabytes) do not; kraken2-build cannot download (--download-taxonomy, --download-library, --standard, --special) and has no --add-to-library – a database is built from sequences, a map and a taxonomy that you put in its folder (see Metagenomics). Reads compressed with bzip2 cannot be read. Kraken2 and Bracken run on one thread.
  • MACS3 is a Python program too: each command starts the same Python, with NumPy, SciPy, scikit-learn and pandas – a few seconds; the first command loads about 45 MB. It runs as one process (callvar -m N works through its N parts one after another, with the same result) and keeps the reads in memory: the reads of a chromosome or of a small genome are fine, a whole human experiment of tens of millions of reads is too much for a browser tab. Its messages say [RSS unavailable] where Linux gives the memory it uses.
  • Bracken: its two Python programs start a Python of their own for each command, as Cutadapt does (a few seconds). Where Bracken's script reports an error but ends with status 0 – a database or a report that is not there – it ends with status 2 here.
  • HMMER runs on one thread: --cpu is left out, with a note. It cannot read files compressed with gzip (.gz) – HMMER starts the program gzip to read them, and a web page cannot start programs: unpack them first (gunzip -k FILE.gz). Easel's own programs (esl-reformat, esl-sfetch …) are not here. HMMER needs WebAssembly SIMD, which all current browsers have. Its line “# CPU time” says 0.00u 0.00s: a web page does not tell a program how much processor time it used (the “Elapsed” time is right). Profile databases as big as the whole of Pfam do not fit in the browser's memory: use the InterPro card of the Databases tab for those.
  • bustools sorts on one thread (sort -t 4 becomes -t 1, with a note) and in 64 MB of memory unless told otherwise – 1 GB at most: a larger -m becomes -m 64M, with a note. Its matrices are those of bustools on Linux; the .ec.txt file that count writes without --genecounts has the same equivalence classes, but those the matrix does not use can be numbered differently.
  • PLINK 2 is built without the LAPACK library, so --pca and --pheno-svd are not available (PLINK says so and stops). It works in 640 MiB of memory, the least it accepts: the terminal adds --threads 1 --memory 640 require unless you give them, and a larger --memory becomes 1024 (more threads than 2 become 2), with a note. --script and --rerun, which read options from a file, are not available: plink2 $(cat FILE) does the same. Its genotypes must fit in that memory – thousands of people and variants, not a whole biobank. It needs a cross-origin isolated page.
  • Strelka2: the somatic workflow, not the germline one. Strelka's workflow scripts are Python 2, which is not here: the terminal runs runWorkflow.py itself, with Strelka's own programs – -m local only, the tasks one after another. python2 runs these scripts and nothing else.

Files

  • Your files are kept in this browser on this computer, not on a server – see where your files are kept.
  • Browsers give a site a share of the free disk space – usually several gigabytes; My files shows how much is used. Files of hundreds of megabytes work, but slowly. Python and R are not given files over 300 MB, and a file over 1 GB is not kept in the browser at all: it is there while the page is open – download it if you need it.
  • Large intermediate files fill the space fast: pipe programs together (minimap2 … | samtools sort -o mapped.bam -) instead of writing a SAM file, and delete what you no longer need.

Installing

  • No sudo, apt or background jobs (&). Programs cannot be added to the terminal – conda install there only models environments.
  • Python packages install with %pip install (pure-Python packages, and those Pyodide has built); R packages with install.packages() (those built for webR). Both last until the page is reloaded.
  • Some packages have no build for the browser yet – mostly those that need system libraries; the error says so. (DESeq2 and edgeR work: locfit, which they need, comes with the workbench.)

The internet

  • Python is downloaded when a Python notebook is open, R when an R notebook is open – and the page opens the last notebook you had open when it starts (a Python one on the first visit) –, packages when they are imported or installed: tens of megabytes, of which the browser keeps a copy for later visits.
  • A web page can only ask web services that allow requests from web pages (CORS). The big bioinformatics services do – Ensembl, UniProt, NCBI, EBI, the PDB, AlphaFold DB and the others of the Databases tab; KEGG and most web pages do not. This holds for notebooks, curl and wget alike.
  • R in the browser can only make GET requests; use Python for POST requests.
  • The Databases tab, the AI assistant, the hosted genomes of the genome browser, downloads from the PDB, and the Networks tab's STRING, IntAct, NDEx and enrichment need the internet all the time.

The tabs

  • Galaxy offers a selection of tools, runs one job at a time, and has no user accounts or shared histories.
  • Snakemake is a browser edition of its commonly used core: rules, wildcards, expand, -n, --dag, --summary; no cluster execution.
  • The 3D viewer needs WebGL (3D graphics in the browser): if it does not start, turn on hardware acceleration in the browser's settings.
  • The Networks tab draws networks of a few thousand nodes smoothly; larger ones (up to 60,000 nodes and 300,000 edges) open, but are slow to draw and to lay out. Statistics and hub rankings follow every shortest path: seconds for a few thousand nodes, about half a minute for 10,000. Cytoscape's apps (plugins) are not here; the most used of them – NetworkAnalyzer, cytoHubba, MCODE, MCL, enrichment – have their equivalents in the tab (Network analysis).
  • The workbench is made for a laptop or desktop screen; on a phone or tablet it works, cramped.

Use a current Chrome, Edge, Firefox or Safari.

When something goes wrong

The usual problems, and what to do about them. Error messages in the notebook and the terminal often carry a hint of their own – and Ask the AI assistant about this error explains them (AI assistant).

Starting

Python or R takes long to start
The first start of a visit downloads the language (tens of megabytes); later visits use the browser's copy and are quicker. The label at the top right of a notebook says what it is doing.
A tab says it could not start
Reload the page (your files are kept). For the 3D viewer: turn on hardware acceleration in the browser's settings. Use a current Chrome, Edge, Firefox or Safari.
The page is slow or stops answering
A long computation is running: Stop it (notebook), or press Ctrl+C in the terminal – once, and what follows the running program is skipped; twice, and the program itself is stopped. Close other heavy tabs of the browser.

Files

My files are gone
They are kept in one browser on one computer – is it the same browser, the same computer, the same web address, and not a private window? If the browser's data for the site was cleared, they cannot be recovered: download what you want to keep (Keep and share your work).
"No such file or directory"
The file is not where the code looked. A notebook works in its own folder (~/notebooks): use full paths such as /data/examples/… or /home/user/… (Python's open() does not understand ~). %pwd or getwd() shows the folder; the Files tab shows the names.
"Read-only file system" or "Permission denied"
/data/examples is read-only: its files cannot be changed, and nothing new can be written into it – not even what a program writes next to its input (samtools faidx writes its index next to the FASTA file). Copy what you need into your home folder and work there.
A PDF "cannot be read as a PDF"
The Files tab draws PDF files itself, so no PDF plug-in of the browser is needed. A file it cannot read is damaged, is not a PDF, or is not finished: a plot that R or Python is still drawing into is written only when it is closed – dev.off() after pdf("plot.pdf") in R, plt.savefig("plot.pdf") or the end of with PdfPages(…) in Python. Download the file to open it with another program.
The space is running out
My files (top right) shows how much is used. Delete large intermediate files – SAM files, unsorted BAM files, trimmed reads – or download and delete them.

Programs and code

"command not found"
The program is not in the workbench: help lists what is. Python packages: %pip install NAME; R packages: install.packages("NAME").
featureCounts, salmon or plink2: "… this page is not" cross-origin isolated
These three programs work on several threads, which a browser allows only in a cross-origin isolated page. Reload the page: the workbench isolates it as it starts. It cannot when the page was not opened over https (or from localhost), or in a browser window that allows no service workers (some private windows) – see programs on several threads.
A variant caller says an index is missing, or that the chromosomes do not match
Index the BAM files (samtools index) and the reference (samtools faidx) – again after a program has written a new BAM file, as lofreq indelqual does. The reference must be the one the reads were mapped to, with the sequence names of the BAM header (samtools view -H file.bam | grep @SQ). See Somatic variants.
bracken: "ERROR: …/database100mers.kmer_distrib does not exist"
Bracken needs the distribution for the length of your reads, and it takes 100 when -r is not given. Give the length: -r 151 for the example data (ls DB/*.kmer_distrib shows which lengths a database has); bracken-build -l LENGTH makes one for another length. See Metagenomics.
Kraken2 leaves most reads unclassified, or names a species that cannot be there
Kraken2 finds only what is in its database: a read of an organism that is not there stays unclassified, or goes to a relative that is – E. coli reads to Shigella, say. Look at what the database holds (kraken2-inspect), raise --confidence, and let Bracken's threshold (-t) leave out species with few reads. See Metagenomics.
prodigal: "Sequence must be 20000 characters"
In its usual mode (-p single) Prodigal learns the genome from the sequences it is given, and fewer than 20,000 bases are too few to learn from. Give it the whole genome – all its contigs in one file – or, for a short sequence or a metagenome, use -p meta.
hmmscan: "Failed to open binary auxfiles … use hmmpress first"
hmmscan searches a collection of profiles that hmmpress has prepared: run hmmpress FILE.hmm first, in a folder of your own – it writes four files next to the profiles, which it cannot do in /data/examples. When hmmpress says "Delete old hmmpress indices first", the collection is pressed already; after changing its profiles, press it again with hmmpress -f FILE.hmm.
hmmsearch or hmmscan: "File format problem in trying to open HMM file"
The file given as the profile is not one – an alignment, or sequences. Build the profile from the alignment first (hmmbuild NEW.hmm ALIGNMENT.sto), and mind the order: the profiles come first and the sequences second, for hmmsearch and hmmscan alike.
plink2: "--pca requires plink2 to be built with LAPACK"
This build of PLINK 2 has no LAPACK, the library its principal components (--pca) and --pheno-svd need: they are not available here. The rest of PLINK works. See Genotypes and association.
plink2 --glm: "invoked without --covar … usually an analytical mistake"
PLINK asks for covariates in an association test – ancestry (principal components), sex, age – because a test without them is usually confounded. Give them with --covar FILE, or, when you are sure, add the modifier: --glm allow-no-covars.
plink2: "Failed to open NAME.psam" (or .pgen, .pvar, .bed …)
--pfile NAME reads three files, NAME.pgen, NAME.pvar and NAME.psam (--bfile NAME: .bed, .bim, .fam): give the name without its ending, and make the files first (plink2 --vcf FILE.vcf.gz --make-pgen --out NAME).
macs3 takes several seconds before it does anything
Each command of MACS3 starts a Python of its own with NumPy, SciPy, scikit-learn and pandas – the first time about 45 MB are loaded. After a command, the next one's Python gets ready in the background: a command typed a little later starts at once.
macs3 callpeak: "MACS3 needs at least 100 paired peaks at + and - strand to build the model"
MACS3 works out the length of the fragments from strong peaks, and found too few: the reads are few, the enrichment is weak, or the genome size is far too large for the reads (-g hs for the reads of one chromosome). Give the fragment length yourself – --nomodel --extsize 200, with the length of the library's fragments – or use the reads as pairs (-f BAMPE, -f BEDPE): MACS3 then sees the fragments. See Peaks.
The peaks of MACS3 do not show in the genome browser
Choose the genome the reads were mapped to – hg19 for the example ChIP-seq (igv --genome hg19 …), sacCer3 for the yeast ATAC-seq: the chromosome names of the peaks must be those of the genome.
A program says it is out of memory, or stops without a message
The data is too big for the browser: take a part of it (samtools view of a region, seqtk sample) – see What is different in the browser.
Python or R forgot my variables
The language was restarted – by Restart, Stop, or a reload of the page. Run the notebook's cells again from the top (Run all).
The terminal does not let me type
The AI agent is working in it: wait, or press Stop in the AI assistant tab.

"Failed to fetch", "no answer", a network error
Either the internet connection is off, or the site does not allow requests from web pages (CORS – KEGG and most web pages do not). Download such files with your browser and upload them in the Files tab.

The other tabs

The genome browser shows nothing
Is the right genome chosen? The chromosome names of the file must be those of the genome (human_CYP2C19 for the example genome, chr10 for hg19/hg38). A BAM file needs its .bai (samtools index), a FASTA genome its .fai (samtools faidx). Reads appear only when you zoom in.

STRING knows proteins: long non-coding RNAs and pseudogenes have none, and Ensembl IDs that Ensembl has retired are not found. Check the species. Versions at the end of Ensembl IDs (ENSG00000120129.5) are taken off before the IDs are sent.

Your data and privacy

The workbench has no server of its own that keeps or sees your work: it runs in your browser. What leaves your computer goes to the public services you use, and only when you use them.

What is kept on your computer

  • Your files – notebooks, results, uploads – and Galaxy's datasets: in this browser's storage for the site (IndexedDB).
  • In the browser's local storage: your last 200 terminal commands; the list of Galaxy's history and its workflows; settings – the open tab and notebook, the help page, the genome, the choices of the AI assistant (not its key), your name in the workbench if you put one in, and your e-mail address for BLAST if you ask to remember it.
  • The AI key: only in the tab's memory, or, if you tick it, until the tab is closed (session storage). Never in a file or in long-term storage.

On a shared computer, the next person who uses the same browser account can see what is stored: download your work, then My files → Start afresh. That deletes your files, Galaxy's history, the terminal's commands and the remembered e-mail address; your name in the workbench and the choices of the AI assistant and of the help pane stay, and the AI key is forgotten when you close the tab. The workbench itself sets no cookies and has no tracking or analytics.
